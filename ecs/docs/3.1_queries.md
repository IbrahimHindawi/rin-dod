# 3.1 Queries

`ecs/src/3.systems/3.1.queries/queries.rin`

**In the dojo:** [6. bitsets](../../dojo/6.bitset/README.md), [12. a watermark](../../dojo/12.watermark/README.md), each on its own, to watch and to practise.

Part 2 finished the storage. Everything from here on is behaviour, and in an
ECS behaviour lives in **systems**: code that runs over every entity with some
set of components. "Every entity with a position and a velocity" isn't in one
place. It's spread over every table whose signature has both bits. So a
system's first job is finding those tables, and the thing that finds them is
a **query**:

```
all {position velocity}, none {}   ->   tables 1, 2, 3
```

A query matches **tables, not entities**. A game has a handful of tables and
rarely makes new ones, so the matching is done once and kept. Each frame, a
system walks the kept list, and inside each table streams the columns.

## First: the storage, ready for systems

Part 3 is about to call kayan from deep inside a frame, and that changes a few
things about the storage. Open this chapter's file beside 2.7's and you'll see
them, so here they are. The design is the same. What moved is who holds what.

**The world remembers its region.** In Part 2, every proc that could allocate took
`r: region level`, and that was fine with `main` at the top of every call. A
system won't have `level` to hand, so the world keeps it, the way a vec keeps its
own:

```rin
kayan_heap: struct = {
    arena: ^memops_arena;
}
```

`kayan_spawn(w, signature)` no longer takes a region. `kayan_heap_make` sets this
up once, inside `kayan_world_make`, and nothing above the byte core hands an arena
around.

**Procs that only read say so.** `kayan_alive`, `kayan_get`, `kayan_verify` and
the printers take `*const kayan_world`.

**Column slices are checked, and the caller says how long it wants one.** This is
the proc every system lives on, and there's no `unsafe` in it:

```rin
kayan_slice: proc<T>(t: *const kayan_table) -> []T in level = {
    id: u32 = kayan_id_of<T>();
    c: option<*kayan_column in level> = t*.columns[id];
    if (!c) {
        printfmt("kayan: the table has no column for component {}\n", id);
        exit(1);
    }
    return kayan_column_slice<T>(c, t*.count);
}
```

The result is `in level`, because that's the truth about the memory. What a caller
does with it is up to the local it goes in. Write `ps: []position`, with no region,
and it's the kind of borrow 2.5 ended on: keep it across a call that may change the
world it came from, and the checker refuses.

```
type error: 'keep' may be stale: 'w', which it was taken from, has been changed since; take it again
```

**Nothing in the core believes the table.** 2.2's rule matters more here, because
now there's a lot of code above the core. rin has no private fields, so any proc
holding a table can write `t*.count`, and `kayan_slice` passes that field straight
down. It's safe anyway. The view measures `count` against the column's slice, and
stops the program if it doesn't fit. A row's bytes are the same story:

```rin
kayan_column_bytes: proc(c: *kayan_column, row: u64) -> []u8 in level = {
    return c*.data[row * c*.size..(row + 1) * c*.size];
}
```

That needs no `unsafe`, and it doesn't ask its caller to keep the row in range.
`data` is a slice, so a wrong row, or a wrong `size`, is a bounds failure wherever it came from.
Every proc above it, however it got its numbers, inherits that. This is the design:
checked code can have every kind of bug, and the worst it can do to a column is
stop the program or get a wrong number.

**The `unsafe { }` blocks are six**, each a few lines with an honest signature,
and every other proc in the file is checked:

- `kayan_heap_make`: keeping the region's arena where the core can reach it;
- `kayan_column_make`, `kayan_table_new`: a column and a table allocated from that
  arena;
- `kayan_column_grow`, `kayan_column_slice`: 2.2's core;
- `kayan_print_builtin`: 2.7's bytes read as a value.

One thing in these blocks is still a field believed on its word: the heap's `arena`
pointer has no bound for anyone to check. rin seals a struct holding a raw pointer
to the file that declares it, so nothing importing this file can write that field.
Inside the file it's on the author: only `kayan_heap_make` writes it. That's the
same line Rust draws at a module, and it's what `unsafe` code owes.

Tables are still allocated one by one and never move. A column still does, and
3.3 is about that.

## Step 1: the query

```rin
kayan_query: struct = {
    all: u64;
    none: u64;
    tables: *vec<u32> in level;
    checked: u64;
}
```

- `all`: a table must have every one of these components.
- `none`: and none of these. "Drones that aren't burning" is
  `all {health}, none {burning}`.
- `tables`: the matching tables, by index. An index is what a slot holds too:
  plain data, a few bytes, with no region to name. `kayan_query_table` turns one
  into a pointer when a walk needs it.
- `checked`: how many of the world's tables the query has looked at.

The list of tables lives in the world's region, so a query is told which region
it's made in. Making one costs nothing: it matches when first updated.

```rin
kayan_query_init: proc(r: region level, all: u64, none: u64) -> kayan_query = {
    return { .all = all, .none = none, .tables = vec<u32>make(r, 4) };
}
```

Matching is two ANDs on the signature:

```rin
kayan_matches: proc(signature: u64, all: u64, none: u64) -> b32 = {
    return (signature & all) == all && (signature & none) == 0;
}
```

## Step 2: keeping it up to date

Tables are only ever *added*, always at the end of `w.tables`, and never
removed. So a query that has checked the first `checked` tables only needs to
look at the ones after that:

```rin
kayan_query_update: proc(w: *const kayan_world, q: *kayan_query) -> void = {
    for (ti: u64 = q*.checked; ti < w*.tables*.length; ti += 1) {
        if (kayan_matches(kayan_table_at(w, cast(ti, u32))*.signature, q*.all, q*.none)) {
            _ = vec<u32>push(q*.tables, cast(ti, u32));
        }
    }
    q*.checked = w*.tables*.length;
}
```

The first update checks every table. After that, a frame with no new tables
costs one comparison. A new table is checked once, by each query, the next
time each is updated. flecs does the same thing in reverse: when a table is
made, it tells the queries.

## Step 3: walking a query

This is the shape of every system:

```rin
        kayan_query_update(w, movers&);
        for (i: u64 = 0; i < movers.tables*.length; i += 1) {
            t: *kayan_table in level = kayan_query_table(w, movers&, i);
            ps: []position = kayan_slice<position>(t);
            vs: []velocity = kayan_slice<velocity>(t);
            for (row: u64 = 0; row < t*.count; row += 1) {
                ps[row].at.x += vs[row].per_second.x * 0.5;
                ps[row].at.y += vs[row].per_second.y * 0.5;
            }
        }
```

Two loops. The outer one is over tables, a few iterations. The inner one is
over rows: two dense arrays, read and written in order. That's lesson 1's
`move_soa`. The query's job is to hand you the arrays; what you do with them
is the same data-oriented loop as always.

The drones and the bullet are in different tables, and the loop doesn't care.
The turret isn't matched (no velocity), and the loop never sees it, not even
to skip it.

The pointers fit the loop. `t` names `level` and can be kept. `ps` and `vs` are
borrows, taken fresh for each table and gone at the end of its turn, which is
exactly as long as a slice into a column should live.

## Run it

```
movers: all {position velocity}, none {}; tables: 2, entities: 4
    table 1 {position velocity health}: 1:1 2:1 3:1
    table 2 {position velocity damage lifetime}: 4:1
targets: all {position health}, none {burning}; tables: 1, entities: 3
    table 1 {position velocity health}: 1:1 2:1 3:1
on_fire: all {health burning}, none {}; tables: 0, entities: 0
```

Then drone `2:1` catches fire, which makes table 3, *after* the queries were
made:

```
2:1 catches fire, and the world makes table 3 for it
the queries have checked 3 tables; updating them checks the new one only
movers: all {position velocity}, none {}; tables: 3, entities: 4
    table 1 {position velocity health}: 1:1 3:1
    table 2 {position velocity damage lifetime}: 4:1
    table 3 {position velocity health burning}: 2:1
targets: all {position health}, none {burning}; tables: 1, entities: 2
    table 1 {position velocity health}: 1:1 3:1
on_fire: all {health burning}, none {}; tables: 1, entities: 1
    table 3 {position velocity health burning}: 2:1
```

`movers` picked up the new table, `targets` refused it (`none {burning}`), and
`on_fire` got its first. Nobody re-scanned the old tables.

Last, the bullet is despawned. Its table is now empty, and stays in `movers`.
Walking an empty table costs one look at `count`.

## Why this is fast

A query's cost doesn't depend on how many entities there are. It depends on
how many *tables* match, and that number is small and stable. 10,000 drones
in one table is one table to visit. That's the payoff of grouping entities by
signature back in 2.4: the "which entities have X and Y?" question gets
answered per table, once, instead of per entity, every frame.

The flip side is archetype fragmentation (2.4's Try): if every entity had a
unique signature, every query would match thousands of one-row tables.
