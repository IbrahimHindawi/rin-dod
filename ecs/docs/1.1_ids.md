# 1.1 An entity is a number

`ecs/src/1.entities/1.1.ids/ids.rin`

An ECS has three parts: **E**ntities, **C**omponents and **S**ystems. This
chapter builds all three in the simplest way that works, about a hundred lines,
so you can see the whole shape before any of it gets clever. The chapters
after this one keep the shape and fix its costs, one at a time.

## The idea

A game is full of *things*: a turret, drones, bullets. An ECS splits each
thing into three parts:

- **An entity** names the thing. It is just a number. It has no data and no
  behaviour of its own.
- **Components** are the thing's data: a position, a velocity, health. Each
  component is plain data, a small struct or a number.
- **Systems** are the behaviour: loops that run over every entity that has the
  components they need. Movement runs over everything with a position and a
  velocity.

A turret is entity 0 with a position and health. A drone is entity 1 with a
position, a velocity and health. Nothing says "turret" or "drone" anywhere;
what a thing *is* comes from which components it has.

## Step 1: the entity

```rin
kayan_entity: struct = {
    index: u32;
}
```

An entity is a number, so why the struct? Because a bare `u32` can be mixed up
with any other `u32`. A proc that takes a `kayan_entity` cannot be handed a
count or a row index by mistake, and the struct costs nothing at run time: it
compiles to the same 4 bytes. It also gives the number room to grow, and in
1.3 it does.

## Step 2: the world

Where do components live? The simplest answer: one array per component, with
one slot for every possible entity, indexed by the entity's number. Beside
each array, a flag per entity saying whether it has that component.

```rin
kayan_world: struct = {
    count: u32;
    positions: [8]vec2;
    has_position: [8]b32;
    velocities: [8]vec2;
    has_velocity: [8]b32;
    healths: [8]f32;
    has_health: [8]b32;
}
```

Look at the shape. This is lesson 1's **struct of arrays**: every position
together, every velocity together. An entity's data is spread across the
arrays, all at the same index. Entity 1's position is `positions[1]` and its
health is `healths[1]`.

## Step 3: spawning

A new entity is the next number:

```rin
kayan_spawn: proc(w: *kayan_world) -> kayan_entity = {
    if (w*.count == 8) {
        printfmt("the world is full\n");
        exit(1);
    }
    e: kayan_entity = { .index = w*.count };
    w*.count += 1;
    return e;
}
```

It has no components yet: every flag for its number is still false.

## Step 4: giving it components

Giving an entity a component is writing the value at its number and raising
the flag:

```rin
set_position: proc(w: *kayan_world, e: kayan_entity, p: vec2) -> void = {
    w*.positions[e.index] = p;
    w*.has_position[e.index] = true;
}
```

`set_velocity` and `set_health` are the same, one per component. Writing one
proc per component type is tedious, and Part 2 replaces all of them with a
single generic `kayan_set<T>`. For now, plain is better: you can see exactly
which bytes get written.

Building a drone is spawning a number and attaching data to it:

```rin
    drone_a: kayan_entity = kayan_spawn(w&);
    set_position(w&, drone_a, { .x = 10.0, .y = 0.0 });
    set_velocity(w&, drone_a, { .x = -1.0, .y = 0.5 });
    set_health(w&, drone_a, 100.0);
```

## Step 5: a system

A system is a loop. Movement runs over everything with a position and a
velocity:

```rin
movement_system: proc(w: *kayan_world, dt: f32) -> u32 = {
    moved: u32 = 0;
    for (i: u32 = 0; i < w*.count; i += 1) {
        if (w*.has_position[i] && w*.has_velocity[i]) {
            w*.positions[i].x += w*.velocities[i].x * dt;
            w*.positions[i].y += w*.velocities[i].y * dt;
            moved += 1;
        }
    }
    return moved;
}
```

It doesn't know about turrets, drones or bullets. It knows about positions
and velocities, and anything that has both moves, including bullets that
didn't exist when the system was written. That's the ECS idea in one proc:
**behaviour attaches to data, not to types of thing.**

## Run it

```
spawned turret 0, drones 1 and 2, bullet 3
    entity 0  position ( 0.00,  0.00)  velocity -                health 500
    entity 1  position (10.00,  0.00)  velocity (-1.00,  0.50)  health 100
    entity 2  position ( 0.00, 10.00)  velocity ( 0.50, -1.00)  health 100
    entity 3  position ( 0.00,  0.00)  velocity ( 4.00,  4.00)  health -
step 1: the movement system looked at 4 entities and moved 3
step 2: the movement system looked at 4 entities and moved 3
...
every component array has room for 8; 4 entities exist
    positions hold 4 values, velocities 3, healths 3
```

The turret has no velocity, so movement skips it. The bullet has no health,
and nothing cares.

## What this costs

It works, and every later chapter keeps this shape: entities are numbers,
components are arrays of plain data, systems are loops. But look at the last
two lines of the output and at the loop:

1. **Every array is as long as the most entities the world can hold.** Velocity
   has room for 8 and holds 3. A game with 10,000 entities and 50 component
   types would have 50 arrays of 10,000, mostly empty.
2. **Every system visits every entity** and checks flags to skip the ones
   that don't apply. Movement looked at 4 and moved 3. With 10,000 entities of
   which 50 move, it would look at 10,000 to move 50.
3. **Nothing can be destroyed.** There's no despawn, and numbers only go up.

The next chapter fixes 3. Chapter 1.4 packs the data so systems stop skipping,
and Part 2 fixes 1 and 2 for good with tables.

## Try

1. Give the turret a velocity and run it. Nothing else changes: the turret
   moves because it now has the data movement wants.
2. Add a `lifetime: [8]f32` component with its flags, and an `aging_system`
   that counts it down. How many places did you have to touch?
3. Spawn a ninth entity. Read the error, then think about what a game would
   need instead of a fixed 8.
