# 2.2 Columns

`ecs/src/2.components/2.2.columns/columns.rin`

**In the dojo:** [4. a type-erased column](../../dojo/4.column/README.md), [8. index, not pointer](../../dojo/8.index/README.md), each on its own, to watch and to practise.

1.4 kept components in typed arrays: `positions: [8]vec2`. A world that
works for any component can't, because it doesn't know the types. It knows,
from the registry, each component's size and alignment, and that's enough.

A **column** is one component's array, kept as bytes. Row `r` is the `size`
bytes starting at `r * size`. Everything a table does with its data is a byte
operation on columns: grow, copy one row over another, zero a new row. None of
it depends on the type. The type comes back only at the edge, where game code
reads a column as `[]T`.

This chapter builds the column and exercises it by hand. 2.3 puts columns in
a table. It's also the first chapter whose memory can grow, so it's the first
that needs a **region**, and the first where the checker can't follow
everything we do. Both of those show up in what a column looks like.

## Step 1: what a column is

A region is memory that ends all at once, an arena with a name the checker can
reason about. The file names one at the top:

```rin
level: region;
```

and `main` opens it around everything that uses it:

```rin
    level: region = {
```

When that block ends, everything allocated in `level` is gone together. There's
nothing to free one piece at a time, and nothing that can be freed too early:
the checker won't let a pointer into `level` outlive it.

```rin
kayan_column: struct = {
    data: []u8 in level;
    size: u64;
    align: u64;
}
```

Bytes, plus how many bytes make a row, plus the alignment to allocate with.
No count and no capacity: every column of a table has the same number of
rows, so the table keeps those once (2.3).

`data` is a slice with a length, every byte the column owns, and `in level` says
where those bytes are. That's a rule, not a comment: a pointer or slice kept in
memory has to name the region it points into. Only a local or a parameter may
leave it off.

A column for a component is made from its reflect record:

```rin
kayan_column_init: proc(c: *kayan_column, info: *const reflect) -> void = {
    c*.size = info*.size;
    c*.align = info*.align;
}
```

Its bytes will be in the region, so the column is too:

```rin
        positions: *kayan_column in level = new<kayan_column>(level);
        healths: *kayan_column in level = new<kayan_column>(level);
        kayan_column_init(positions, position<>&);
        kayan_column_init(healths, health<>&);
```

## Step 2: rows are byte offsets

```rin
kayan_column_row: proc(c: *kayan_column, row: u64) -> []u8 in level = {
    return c*.data[row * c*.size..(row + 1) * c*.size];
}
```

That's the whole addressing scheme: `row * size`. With it, copying and zeroing
rows are plain loops over bytes:

```rin
kayan_column_copy_row: proc(c: *kayan_column, to: u64, from: u64) -> void = {
    for (i: u64 = 0; i < c*.size; i += 1) {
        c*.data[to * c*.size + i] = c*.data[from * c*.size + i];
    }
}

kayan_column_zero_row: proc(c: *kayan_column, row: u64) -> void = {
    for (i: u64 = 0; i < c*.size; i += 1) {
        c*.data[row * c*.size + i] = 0;
    }
}
```

`kayan_column_copy_row` is swap-remove's copy from 1.4, for any component. These
are loops rather than `memcpy` and `memset` because those two take raw pointers
and nothing checks what they do with them. Because `data` has a length, these
loops are ordinary checked code: a row past the end stops the program, in every
build, instead of writing over a neighbour.

## Step 3: growing

```rin
kayan_column_grow: proc(r: region level, c: *kayan_column, count: u64, capacity: u64) -> void = {
    unsafe {
        raw: ^u8 = cast(memops_arena_push_zero(r, c*.size * capacity, c*.align), ^u8);
        bytes: []u8 in level = cast(raw[0..c*.size * capacity], []u8 in level);
        // Slicing checks both ends: a count past either block stops the program.
        kept: u64 = c*.size * count;
        slice<u8>copy(bytes[0..kept], c*.data[0..kept]);
        c*.data = bytes;
    }
}
```

A new block for `capacity` rows, with the rows in use copied over. The old
block stays in the region, unused: a region frees everything at once, never
one allocation. Doubling the capacity each time keeps the waste to at most
the size of what's in use, and the copies to a few per table over a whole
game.

`r: region level` is how a proc asks for the right to allocate: a region
parameter says which region, so you can read off a signature whether a proc can
allocate at all, and where.

This is the first `unsafe { }` in the course, and it's here because of what a
column is. Checked code can allocate a `[]T` with `new_slice<T>`, which knows `T`.
A column doesn't know `T`. It has a size and an alignment as run-time numbers, and only
the arena can hand back bytes aligned for them. So this proc goes under the
checker: it calls the arena directly, and casts what comes back. An `unsafe { }`
block is the author saying "I keep the rules here myself", and everything outside
it takes the proc's signature at its word. The course calls a proc like this
**trusted**. Its signature has to be honest: this one says the bytes end up in
`level`, and they do.

Notice what the block does straight after it gets its bytes: it turns them into a
slice, and copies with std's checked `slice<u8>copy` rather than `memcpy`. Why
bother, when the rows in use are right there in `count`? Step 4 answers that.

This is also why **pointers into a column go stale**: after a grow, the data
is somewhere else. Notice what stale means here, because it's what makes the
shape safe. The old block is still in the region. A pointer into it reads good
memory holding old values. It can be *wrong*, but it can't be *dangling*, since
no block in `level` goes away before `level` does. 2.5 shows it happening.

## Step 4: the typed view

```rin
kayan_column_slice: proc<T>(c: *const kayan_column, count: u64) -> []T in level = {
    if (c*.size != sizeof(T)) {
        printfmt("kayan: a column of {}-byte rows read as a {}-byte type\n", c*.size, sizeof(T));
        exit(1);
    }
    if (!reflect_is_plain(T<>&)) {
        printfmt("kayan: a column holds plain data, and this {}-byte type is not\n", sizeof(T));
        exit(1);
    }
    if (count > c*.data.length / sizeof(T)) {
        printfmt("kayan: a view of {} rows on a column with room for {}\n", count, c*.data.length / sizeof(T));
        exit(1);
    }
    unsafe {
        if (cast(c*.data.data, usize) % alignof(T) != 0) {
            printfmt("kayan: a column's bytes are not aligned to {}\n", alignof(T));
            exit(1);
        }
        raw: ^T = cast(c*.data.data, ^T);
        return cast(raw[0..count], []T in level);
    }
}
```

This is the untyped/typed split in one proc. Below it, bytes. Above it, a
`[]T` that game code indexes like any slice, bounds checked in every build. The
cast from bytes to `T` is the reinterpretation itself, the second thing a checker
can't see through, so this is the chapter's second `unsafe { }`. It's four
checks and a cast, and only the last check and the cast are inside the block.

To see why so many checks, ask what an `unsafe` block is allowed to believe.

rin has no private fields. Any checked code holding a `*kayan_column` can write
`c*.size`, or cut `c*.data` short, and any caller can pass any `count`. Nothing
stops them, and nothing should have to. So an `unsafe` block can't believe a field
or an argument just because the code that normally sets it is correct. It can only
believe a value that carries its own bound, which is what a slice does: it knows
its length, and checked code can only get one by allocating it or cutting another.
So here's what the view checks, rather than believes:

- **Room.** `count` comes from a table, but the view measures it against the
  slice, the one thing no field can lie about. It divides rather than multiplies,
  so a huge `count` can't overflow its way past the test.
- **Plain data.** `reflect_is_plain` looks at `T`'s record: numbers, enums, and
  structs and arrays of those, with no pointer anywhere. For such a `T`, *any*
  bytes are a valid `T`. That's what makes this safe. It also means `T` has to be a
  struct or an enum, since `T<>` has no record for a bare number.
- **Alignment.** The bytes came from the arena at `c*.align`, but `c*.align` and
  `c*.data` are both just fields, so the block tests the address itself.
- **Size.** This one catches a mistake. It isn't what keeps the view safe: `position`
  and `health` are both 8 bytes, so reading one as the other passes every check.
  You get wrong numbers, and never a bad pointer, because neither has a pointer in
  it. Which is the same promise 2.5 is about to make for a stale pointer: a wrong
  answer, never a bad address.

Now look back at the grow. It takes its `count` from the caller and its sizes from
fields, so it doesn't believe those either. It cuts both blocks to the rows it was
told to keep, and a count past either one stops the program before a byte moves.

Those two blocks are the whole unsafe core of the type-erased column, and they're
small on purpose. The rest of the chapter is checked, and so is everything built
on it for the rest of the course. And since the blocks check what they're handed,
a mistake in the checked code above them stops the program instead of corrupting
memory.

Writing goes through the typed view too:

```rin
            ps: []position = kayan_column_slice<position>(positions, count);
            hs: []health = kayan_column_slice<health>(healths, count);
            ps[row] = { .at = { .x = cast(i, f32), .y = 1.0 } };
            hs[row] = { .points = 50.0 + 10.0 * cast(i, f32), .max = 100.0 };
```

(Writing `kayan_column_slice<position>(...)[row] = ...` in one line would be
nicer. rin doesn't allow indexing a call's result directly yet, because the
bounds check would evaluate the call twice. Hence the locals.)

## Step 5: rows stay rows across columns

The program keeps two columns side by side, positions and healths, and moves
them together:

```rin
        last: u64 = count - 1;
        kayan_column_copy_row(positions, 1, last);
        kayan_column_copy_row(healths, 1, last);
        count -= 1;
```

Same operation, each column using its own row size. Row 1 is still one
entity's data across both columns. That's a table in all but name.

## Run it

```
a position column has 8-byte rows, a health column 8-byte rows
    grew to room for 2 rows
    grew to room for 4 rows
    grew to room for 8 rows
five rows, written through the typed view:
    row 0  position ( 0.00,  1.00)  health  50 / 100
    row 1  position ( 1.00,  1.00)  health  60 / 100
...
row 1's health as the column stores it, bytes: 00 00 70 42 00 00 c8 42
    that is 60.0 and 100.0 as little-endian f32s; the column never knew
swap-removed row 1: row 4 moved into it, in both columns
```

The byte line is the point of the chapter. `00 00 70 42` is `60.0` as an
`f32`, and the column stored it without knowing it was a float, or a health,
or anything at all.

## Try

1. Add `damage: struct = { amount: f32; }`, read the health column as `[]damage`
   (4-byte rows) and run it. Read the message.
2. Start the capacity at 1 instead of 2. How many grows does it take to fit 5
   rows? What if it grew by 1 each time instead of doubling?
3. Print the bytes of a position row. Which bytes are `x` and which are `y`?
4. Take the `unsafe { }` off `kayan_column_grow` and compile. Read each thing
   the checker objects to. Which of them could a column avoid, knowing only a
   size and an alignment?
5. Read the position column as `[]health`. Every check passes. What are row 3's
   `points` and `max`, and why is this wrong but not dangerous?
6. Add a component with a pointer in it, `holder: struct = { at: *position in level; }`,
   and read the health column as `[]holder`. It's the right size. Why would it be
   dangerous if this view let it through?
7. Break the column on purpose, from checked code: after the rows are written, add
   `positions*.data = positions*.data[1..positions*.data.length];`. `rin check`
   has no objection. Run it. Then try `count = 1000;`, and
   `kayan_column_zero_row(positions, 1000);`. Who stops each one?
