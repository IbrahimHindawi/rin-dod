# 2.7 Inspecting the world

`ecs/src/2.components/2.7.inspecting/inspecting.rin`

The world can store, copy and move any component, but it can't show you one.
When something goes wrong at frame 3,000, you want to see an entity: every
component it has, every field, with names. In C that means writing a printer
per component and keeping each in step with its struct. In rin, the compiler
already wrote down everything a printer needs. Each component's **reflect
record** lists its fields with their names, types and byte offsets. The world
registered those records back in 2.1 to learn component sizes. Here they pay
off a second time.

```
kayan_inspect(w, e)       every component of e, field by field
kayan_print_layout(w)     every table, its columns, and their memory
```

Neither names a single component type. Add a component tomorrow and both
print it.

## Step 1: a component as bytes

Tools work from reflect records, not types, so they need the byte view:

```rin
kayan_get_bytes: proc(w: *kayan_world, e: kayan_entity, id: u32) -> []u8 = {
    none: []u8 = {};
    if (!kayan_alive(w, e) || id >= w[0].component_count) {
        return none;
    }
    slot: *kayan_slot = vec<kayan_slot>at(w[0].slots&, cast(e.index, u64));
    t: *kayan_table = kayan_table_at(w, slot[0].table);
    if (!kayan_table_has(t, id)) {
        return none;
    }
    c: *kayan_column = t[0].columns[id]&;
    row: u64 = cast(slot[0].row, u64);
    all: []u8 = c[0].data[0..t[0].count * c[0].size];
    return all[row * c[0].size..(row + 1) * c[0].size];
}
```

It's `kayan_get<T>`'s path, stopping one step early: the row's bytes as a
slice, sized by the column. Game code uses the typed layer; tools use this.

## Step 2: walking fields

```rin
kayan_print_fields: proc(type: *const reflect, base: []const u8, depth: u32) -> void = {
    fields: [*]const reflect_field = reflect_fields(type);
    for (i: u64 = 0; i < type[0].count; i += 1) {
        f: *const reflect_field = fields[i]&;
        if (reflect_field_has_attr(f, "hidden")) {
            continue;
        }
        at: []const u8 = base[f[0].offset..f[0].offset + f[0].size];
        kayan_indent(depth);
        printf("%s:", f[0].name);
        info: *const reflect = f[0].info;
        if (info != null && info[0].kind == reflect_kind_struct) {
            printf("\n");
            kayan_print_fields(info, at, depth + 1);
        } else {
            printf(" ");
            kayan_print_builtin(f[0].type, at);
            printf("\n");
        }
    }
}
```

For each field the record says, cut its bytes out of the component by offset
and size. A struct field (`at: vec2` inside `position`) has a record of its
own, so the printer recurses into it. A builtin field (`f32`, `u32`) is
printed by its type's name.

Because each field's bytes are cut with a bounds-checked slice, a record that
disagreed with the data would stop a Debug build instead of printing garbage.

## Step 3: hiding bookkeeping

Fields can carry tags with `@`:

```rin
turret: struct = { cooldown: f32; timer: f32 @ "hidden"; }
```

The inspector skips anything tagged `"hidden"`. The component decides what a
tool shows; the tool doesn't need to know the component.

## Step 4: an entity, and the layout

`kayan_inspect` walks the entity's signature and prints each component with
`kayan_print_fields`. `kayan_print_layout` walks every table and prints each
column's row size and bytes used out of bytes allocated, which shows where
memory goes.

## Run it

```
0:1 {position turret}
    position
        at:
            x: 0.00
            y: 0.00
    turret
        cooldown: 0.50
...
2:1 {position velocity health burning}
...
    health
        points: 60.00
        max: 100.00
    burning
        per_second: 10.00
...
1:1 (dead)
```

```
table 1 {position velocity health}: 0 rows, room for 4
    position   8 bytes a row,    0 of   32 bytes in use
    velocity   8 bytes a row,    0 of   32 bytes in use
    health     8 bytes a row,    0 of   32 bytes in use
```

The turret's `timer` isn't printed. Table 1 is empty but keeps its capacity:
drone `1:1` was its only remaining row after `2:1` caught fire and moved out,
and then `1:1` was despawned. Tables never shrink in this course. A real
engine might trim empty ones between levels.

## Part 2 in one picture

```
handle 2:1 ──> slots[2] { generation 1, table 2, row 0 }
                                         │
table 2 {position velocity health burning}
  entities  [ 2:1 ]
  position  [ (30, -5) ]     velocity [ (-1, 0) ]     health [ 60/100 ]     burning [ 10 ]
  add_edges / remove_edges ──> neighbouring tables in the archetype graph
```

The storage half of the ECS is done: identity (Part 1), and any component, in
any combination, changing at run time (Part 2). Part 3 is the behaviour:
queries to find tables, and systems to run over them.

## Try

1. Add a field to `health` and run it. Nothing in the inspector changes.
2. Tag `health.max` as hidden.
3. Write `kayan_set_f32_by_name(w, e, "health", "points", 10.0)` with the
   reflect records: find the component by name, the field by name, check it's
   an `f32`, write it. That's the core of an editor or a console.
