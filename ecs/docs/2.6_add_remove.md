# 2.6 Adding and removing components

`ecs/src/2.components/2.6.add_remove/add_remove.rin`

A drone catches fire: it gains a `burning` component. The fire goes out: it
loses it. Changing *what* an entity is, while the game runs, is the thing
your C kayan couldn't do, because its archetypes were structs fixed at compile
time. In an archetype ECS a table holds exactly one combination, so a drone
that gains a component no longer belongs in its table. **It moves:**

1. find the table for its signature plus (or minus) the component;
2. add a row there, and copy every component the two tables share;
3. swap-remove its old row, fixing whoever moves into the hole;
4. point its slot at the new table and row.

Its handle doesn't change. Everything else about it is where it was, one
table over.

## Step 1: the move

```rin
kayan_move: proc(w: *kayan_world, e: kayan_entity, to_index: u32) -> void = {
    slot: *kayan_slot = vec<kayan_slot>at(w[0].slots&, cast(e.index, u64));
    from_index: u32 = slot[0].table;
    if (from_index == to_index) {
        return;
    }
    from: *kayan_table = kayan_table_at(w, from_index);
    to: *kayan_table = kayan_table_at(w, to_index);
    from_row: u64 = cast(slot[0].row, u64);
    to_row: u64 = kayan_table_add_row(w, to, e);
    for (id: u32 = 0; id < w[0].component_count; id += 1) {
        if (kayan_table_has(from, id) && kayan_table_has(to, id)) {
            memcpy(kayan_column_row(to[0].columns[id]&, to_row),
                kayan_column_row(from[0].columns[id]&, from_row), from[0].columns[id].size);
        }
    }
    kayan_table_remove_row(w, from, from_row);
    slot[0].table = to_index;
    slot[0].row = cast(to_row, u32);
}
```

Every piece is something you've already built: `kayan_table_add_row` (2.3), a
byte copy per shared column (2.2), `kayan_table_remove_row` with its slot fix
(1.4). Components only the new table has start zeroed (add_row zeroes them).
Components only the old table has disappear with the old row.

A move costs one row copy in and one row copy out. That's cheap, but not
free, and it's why components that flip on and off every frame are sometimes
better as a field (a `bool on_fire` inside `health`) than as a component.

## Step 2: add and remove, typed

```rin
kayan_add: proc<T>(w: *kayan_world, e: kayan_entity, value: T) -> kayan_status = {
    if (!kayan_alive(w, e)) {
        return kayan_status.dead;
    }
    if (!kayan_has<T>(w, e)) {
        from: u32 = vec<kayan_slot>at(w[0].slots&, cast(e.index, u64))[0].table;
        kayan_move(w, e, kayan_table_with(w, from, kayan_id_of<T>()));
    }
    return kayan_set<T>(w, e, value);
}
```

If the entity already has a `T`, adding is just setting. Otherwise it moves
to the table *with* `T`, then sets it. `kayan_remove<T>` is the mirror image:
`missing` if it has no `T`, otherwise a move to the table *without* `T`.

## Step 3: the archetype graph

Which table is "the table with `T`"? Its signature is the old one plus `T`'s
bit, so it could be looked up in `by_signature` every time. But a game
toggling components does that constantly, always between the same few
tables. So **each table remembers its neighbours**:

```rin
kayan_table: struct = {
    signature: u64;
    count: u64;
    capacity: u64;
    entities: [*]kayan_entity;
    columns: [64]kayan_column;
    add_edges: [64]u32;
    remove_edges: [64]u32;
}
```

`add_edges[id]` is where this table's entities go when they gain component
`id`. `remove_edges[id]` is where they go when they lose it. Each is stored as
*index + 1*, so the zero a new table starts with means "not known yet", with
no initialization pass.

```rin
kayan_table_with: proc(w: *kayan_world, from: u32, id: u32) -> u32 = {
    edge: u32 = kayan_table_at(w, from)[0].add_edges[id];
    if (edge != 0) {
        w[0].edge_hits += 1;
        return edge - 1;
    }
    w[0].lookups += 1;
    to: u32 = kayan_table_for(w, kayan_table_at(w, from)[0].signature | kayan_bit(id));
    // kayan_table_for can move the tables, so both pointers are taken after it.
    kayan_table_at(w, from)[0].add_edges[id] = to + 1;
    kayan_table_at(w, to)[0].remove_edges[id] = from + 1;
    return to;
}
```

The first move from `{position velocity health}` with `burning` looks the
table up (and makes it). It then writes the answer on **both** tables: an add
edge one way and a remove edge back. After that, catching fire and putting it
out both follow edges. The tables and their edges form a graph, the
**archetype graph**, and flecs is built around it.

## Run it

```
4 drones:
    table 0 {position velocity health}: 0:1 1:1 2:1 3:1
frame 1
    0:1 catches fire: ok
    2:1 catches fire: ok
    table 0 {position velocity health}: 3:1 1:1
    table 1 {position velocity health burning}: 0:1 2:1
frame 2
    0:1 is put out: ok
    1:1 catches fire: ok
    2:1 catches fire: ok
...
frame 3
    1:1 is put out: ok
    2:1 is put out: ok
    3:1 is put out: missing
    3:1 catches fire: ok
...
2:1 moved tables twice and kept its data: at (30.00, 0.00), health 100
moves that looked up a table by signature: 1; that followed an edge: 6
kayan_verify: 0 problems
```

Watch row order shuffle as entities move: `3:1` jumps to row 0 of table 0
when `0:1` leaves. Order is never promised, and swap-remove is why. And one
lookup for seven moves: that's the graph working.
