# 2.4 Many tables: archetypes

`ecs/src/2.components/2.4.archetypes/archetypes.rin`

**In the dojo:** [3. the slot map](../../dojo/3.slot_map/README.md), [8. index, not pointer](../../dojo/8.index/README.md), [9. interning](../../dojo/9.interning/README.md), each on its own, to watch and to practise.

2.3's world had one table, so every entity had the same components. Real
games mix: a turret has a position and a turret component, a drone has a
position, velocity and health, a bullet has a position, velocity, damage and
lifetime. Each combination gets **a table of its own**. Every row of a table
has every component in its signature, so there are no holes and no flags.
A table for one combination is called an **archetype**.

```
table 0 {position turret}                   0:1
table 1 {position velocity health}          1:1 2:1 3:1
table 2 {position velocity damage lifetime} 4:1 5:1
```

Nobody declares the archetypes. The first time something spawns with a new
combination, the world makes its table and remembers it by signature, so the
next spawn finds it.

## Step 1: slots say which table

```rin
kayan_slot: struct = {
    generation: u32;
    table: u32;
    row: u32;
}
```

Handle to slot to **(table, row)**. That's the whole entity index from here
on.

## Step 2: the world keeps every table

```rin
kayan_world: struct = {
    infos: [64]option<*const reflect in permanent>;
    component_count: u32;
    tables: *vec<*kayan_table in level> in level;
    by_signature: *hashmap<u64, u32> in level;
    slots: *vec<kayan_slot> in level;
    free: *vec<u32> in level;
    live: u64;
}
```

`tables` holds them all, and `by_signature` maps a signature to its table's
index.

Look at the type of `tables`: a vec of *pointers* to tables. The obvious shape is
a `vec<kayan_table>`, with the tables themselves side by side. It has a classic
bug. Making a new table can grow the vec and move every table in memory, so a
pointer to a table is only good until the next table is made. It works until the
first new archetype appears mid-game. The checker would catch that one, calling
any such pointer kept across a push "may be stale", but then every proc holding a
table would be fighting it.

So instead of being careful, the design removes the problem. Each table is
allocated once, on its own, in the region, and **a table never moves**. The vec of
pointers may grow, but what it points at stays where it is, so
`*kayan_table in level` means just what it says: good for as long as the level
is, across anything. That costs one extra pointer hop per table, not per row, and
the loops that matter never see it.

```rin
kayan_table_at: proc(w: *kayan_world in level, index: u32) -> *kayan_table in level = {
    return vec<*kayan_table in level>at(w*.tables, cast(index, u64))*;
}
```

Slots still name their table by index. A slot is plain data: 4 bytes rather than
8, no region to name, and an index can be stored anywhere.

## Step 3: where archetypes come from

```rin
kayan_table_for: proc(r: region level, w: *kayan_world in level, signature: u64) -> u32 = {
    found: option<*u32> = hashmap<u64, u32>get(w*.by_signature, signature);
    if (found) {
        return found*;
    }
    index: u32 = cast(w*.tables*.length, u32);
    t: *kayan_table in level = new<kayan_table>(r);
    kayan_table_init(w, t, signature);
    _ = vec<*kayan_table in level>push(w*.tables, t);
    _ = hashmap<u64, u32>set(w*.by_signature, signature, index);
    return index;
}
```

Found, or made. A game has tens of archetypes, maybe a few hundred, so a
linear search would do too. The hashmap costs two lines with rin's std, and
2.6 makes the lookup rare anyway. A lookup that can miss returns an `option`, the
same as `get_position` in 1.3.

## Step 4: spawning takes a signature

```rin
kayan_spawn: proc(r: region level, w: *kayan_world in level, signature: u64) -> kayan_entity = {
```

and puts the new entity in that signature's table:

```rin
    table_index: u32 = kayan_table_for(r, w, signature);
    t: *kayan_table in level = kayan_table_at(w, table_index);
    row: u64 = kayan_table_add_row(r, w, t, e);
    // Both calls were handed the world, so the pointer into the slots is
    // taken after them.
    slot: *kayan_slot = vec<kayan_slot>at(w*.slots, cast(e.index, u64));
    slot*.table = table_index;
    slot*.row = cast(row, u32);
```

Note the order. `t` isn't the pointer to worry about any more, since tables don't
move. `slot` is: slots are items in a vec, right there in the vec's storage. Take
it before those two calls, and the checker stops you:

```
type error: 'slot' may be stale: 'w.slots', which it was taken from, has been changed since; take it again
```

`kayan_table_for` grows `tables`, not `slots`, but the checker doesn't track which
of the world's vecs a call changes. It sees a call that may change the world, and
it ends every borrow from that world. So the rule is simple: do the calls first,
take the pointer into a vec last, and use it right away.

Despawning finds the table through the slot, and avoids the question another way:

```rin
    slot: kayan_slot = vec<kayan_slot>at(w*.slots, cast(e.index, u64))*;
    kayan_table_remove_row(w, kayan_table_at(w, slot.table), cast(slot.row, u64));
```

The `*` at the end copies the slot out. A copy can't go stale, and it's two
numbers and a generation, so that's nearly always the easy way.

## Step 5: the invariant, over every table

`kayan_verify` now walks every table: each row belongs to a live entity whose
slot points back at **that table and row**, and the rows of all tables add up
to the live count. Same invariant, one more field.

## Step 6: one column, many tables

The end of the program reads every position in the world:

```rin
        for (ti: u32 = 0; ti < cast(w*.tables*.length, u32); ti += 1) {
            t: *kayan_table in level = kayan_table_at(w, ti);
            ps: []position in level = kayan_slice<position>(t);
```

The position column of each table, in turn. Positions are no longer one
array; they're one array per archetype that has them. This is exactly what a
query does in Part 3: visit the tables that have the right components, and
stream their columns.

## Try

1. Spawn a "drone with damage" (position, velocity, health, damage). How many
   tables now?
2. Spawn 100 entities with 100 different signatures (use the bits of a
   counter). What does that do to a system that visits tables? This is called
   *archetype fragmentation*.
3. In `kayan_spawn`, take `slot` before `kayan_table_for`, and read the error.
   Then get a table pointer before `kayan_table_for`, spawn something with a new
   signature, and use the pointer afterwards. Why does the checker have no
   complaint this time?
