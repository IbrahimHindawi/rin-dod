# 3.4 A game

`ecs/src/3.systems/3.4.game/game.rin`

**In the dojo:** this chapter puts all five building blocks together; [the dojo](../../dojo/README.md) has each one on its own, to watch and to practise.

Everything together. Three lanes, a turret at the left end of each, and
drones coming from the right in waves:

- a turret fires down its lane while there's a drone in it;
- a bullet that reaches a drone damages it;
- a drone below half health catches fire;
- a drone with no health left is destroyed;
- a drone that gets to the left end has reached the base.

The top of the file is kayan, exactly as 3.3 left it. The game is the bottom:
components, kernels, systems, a schedule and a level script. Every rule of
the game is a system over a query. Every structural change a system makes is
a command.

## The pieces

The components are the same seven from 2.1. A drone is a signature:

```rin
drone_signature: proc() -> u64 = {
    return kayan_mask_of<position>() | kayan_mask_of<velocity>() | kayan_mask_of<health>();
}
```

A burning drone is that plus `burning`, which puts it in another table. There
is no `drone` type anywhere in the program. A drone is whatever lives in a
table with these columns.

What the systems share (the drones query, the clock, the score) is one
struct, handed to the systems that need it through `ctx`:

```rin
game: struct = {
    drones: kayan_query;
    time: f32;
    fired: u32;
    hits: u32;
    fires: u32;
    kills: u32;
    breaches: u32;
    came: u32;
}
```

## The schedule

```rin
    systems: [9]kayan_system = {};
    systems[0] = kayan_system_init("turret", shooting, 0, turret_system, g&);
    systems[1] = kayan_system_init("age", kayan_mask_of<lifetime>(), 0, age_system, null);
    systems[2] = kayan_system_init("expire", kayan_mask_of<lifetime>(), 0, expire_system, null);
    systems[3] = kayan_system_init("move", movers, 0, move_system, null);
    systems[4] = kayan_system_init("hit", bullets, 0, hit_system, g&);
    systems[5] = kayan_system_init("ignite", kayan_mask_of<health>(), kayan_mask_of<burning>(), ignite_system, g&);
    systems[6] = kayan_system_init("burn", kayan_mask_of<health>() | kayan_mask_of<burning>(), 0, burn_system, null);
    systems[7] = kayan_system_init("die", kayan_mask_of<health>(), 0, die_system, g&);
    systems[8] = kayan_system_init("breach", kayan_mask_of<position>() | kayan_mask_of<health>(), 0, breach_system, g&);
```

Read it as the frame, top to bottom. Each line's position is a data-flow
decision (3.2):

- `move` before `hit`: bullets hit where they are, not where they were.
- `hit` before `ignite`, `burn` and `die`: a drone takes damage, catches fire
  and is destroyed in the same frame its health drops.
- `die` before `breach`: only a drone that survived the frame can reach the
  base. `breach` also checks `health > 0` itself, because both run in the same
  frame and `die`'s despawn hasn't been applied yet.
- `ignite` has `none {burning}`: a drone catches fire once. The add is a
  command, so next frame it's in the burning table and the query no longer
  matches it.

## The rules

Each one is a few lines. The ones that only change values call kernels:

```rin
burn_system: proc(it: *kayan_iter) -> void = {
    burn(kayan_slice<health>(it*.table), kayan_slice<burning>(it*.table), it*.dt);
}
```

The ones that change structure record commands:

```rin
        if (hs[row].points < 0.5 * hs[row].max && hs[row].points > 0.0) {
            kayan_defer_add<burning>(it*.world, es[row], { .per_second = 10.0 });
            g*.fires += 1;
        }
```

The turret is the most involved. It asks the drones query whether anything
is ahead of it in its lane, then spawns a bullet with a pending spawn (3.3):

```rin
        if (ts[row].timer <= 0.0 && drone_ahead(it*.world, g, ps[row].at.x, ps[row].at.y)) {
```

`hit` is 3.3's hit system, with one extra thought about speed. A bullet
moves a unit a frame and a fast drone a quarter, so they close by at most
1.25 a frame. A hit window of ±0.75 is 1.5 wide, so no bullet can pass
through a drone between two frames:

```rin
                if (dx * dx < 0.5625 && dy * dy < 0.25) {
```

## The level

The waves aren't a system. They're the level script, and it runs **between**
frames, in the game loop, where spawning directly is safe:

```rin
    for (frame: u32 = 0; frame < frames; frame += 1) {
        g.time = cast(frame, f32) * dt;
        if (frame % 32 == 0 && frame / 32 < 8) {
            send_wave(w&, g&, frame / 32);
        }
        kayan_progress(w&, systems, dt);
        problems += kayan_verify(w&);
```

`kayan_verify` runs after every frame: 512 checks of Part 1's invariant over
the whole world.

## Drawing by table

The picture of the lanes walks a query of everything with a position. What
an entity is drawn as comes from its **table's signature**, decided once per
table, not per entity:

```rin
glyph_of: proc(signature: u64) -> i32 = {
    if ((signature & kayan_mask_of<turret>()) != 0) {
        return 'T';
    }
    if ((signature & kayan_mask_of<burning>()) != 0) {
        return '*';
    }
    if ((signature & kayan_mask_of<health>()) != 0) {
        return 'd';
    }
    return '-';
}
```

In an OOP engine this would be a virtual `draw()` per object. Here it's a
property of a table, and the inner loop is a plain loop over positions.

## Exact on purpose

Every speed and time step is a power of two: `dt` is 1/16, drones move 2 or 4
units a second, bullets 16, fire burns 10 a second (0.625 a frame). So every
position, health and timer is exactly representable, and no rounding ever
happens. That's why a Debug build, a Release build, gcc, clang and a CPU that
fuses multiply-adds all print the same game. Real games give that up for
nicer numbers. Rounding differences usually don't matter, but they do the
day you want a replay or a lockstep network game.

## What you built

```
Part 1  entities       handles, generations, slots, swap-remove, kayan_verify
Part 2  components     ids, columns, tables, archetypes, typed access,
                       moving between tables, the archetype graph, reflection
Part 3  systems        queries, kernels and schedules, commands, a game
```

That's a working archetype ECS, about 650 lines of kayan without comments.
It's the design flecs is built on (tables, the archetype graph, cached queries,
command buffers), and Bevy and Unity DOTS are close cousins, minus their years
of features.

Things worth adding next, roughly in order of how much they teach:

- **Relationships**: `child_of(parent)` as a component, flecs' big idea.
- **Change detection**: a per-column version number, so a system can skip
  tables nothing wrote to.
- **Parallel systems**: systems that don't write what others read can run at
  the same time. The schedule already holds what you need to decide that.
- **Removing empty tables**, and the queries' table lists with them.
- **Serialization**: the reflect records already describe every byte; write
  the tables out and read them back.
