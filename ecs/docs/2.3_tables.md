# 2.3 A table

`ecs/src/2.components/2.3.tables/tables.rin`

**In the dojo:** [2. swap-remove and the back-reference](../../dojo/2.swap_remove/README.md), [4. a type-erased column](../../dojo/4.column/README.md), each on its own, to watch and to practise.

The two halves meet. Part 1 built the entity index: handles, slots, packed
rows, swap-remove. 2.1 and 2.2 built the component side: ids, a registry,
columns of bytes. A **table** is 1.4's packed rows with the typed arrays
replaced by columns, one per component in its signature:

```
table {position velocity health}
  entities  [ 0:1 | 3:1 | 2:1 | ... ]     who owns each row
  columns   position [ ... ]  velocity [ ... ]  health [ ... ]
  count, capacity                         shared by every column
```

Row `r` is entity `entities[r]`, and its components are row `r` of every
column. This world still has a single table, so every entity has the same
components; 2.4 gives each combination its own.

## Step 1: the table

```rin
kayan_table: struct = {
    signature: u64;
    count: u64;
    capacity: u64;
    entities: []kayan_entity in level;
    columns: [64]kayan_column;
}
```

- `signature` says which components the table has.
- `columns[id]` is in use when the signature has bit `id`. The rest stay
  zeroed. 64 slots indexed by id means finding a column is an index, never a
  search. kayan in C looked columns up by name in a hash map, which is the
  thing this replaces.
- `count` and `capacity` belong to the table, shared by every column and by
  `entities`, so they can't disagree.

A table is made from a signature and the registry:

```rin
kayan_table_init: proc(w: *kayan_world in level, t: *kayan_table, signature: u64) -> void = {
    t*.signature = signature;
    for (id: u32 = 0; id < 64; id += 1) {
        if ((signature & kayan_bit(id)) != 0) {
            info: option<*const reflect in permanent> = id < w*.component_count ? w*.infos[id] : null;
            if (!info) {
                printfmt("kayan: signature {} uses component {}, which was never registered\n", signature, id);
                exit(1);
            } else {
                kayan_column_init(t*.columns[id]&, info);
            }
        }
    }
}
```

The signature *is* the column list. In the C kayan, the signature and the
columns were written separately and could disagree (archetype `D` had
position columns its signature didn't mention). Here one is made from the
other. A registry slot may be null (2.1), so the test isn't optional: the checker
won't let `info` reach `kayan_column_init` until the empty case has been dealt
with.

## Step 2: rows, for every column at once

Adding a row grows every column together when the table is full, then zeroes
the new row in each:

```rin
kayan_table_add_row: proc(r: region level, w: *kayan_world in level, t: *kayan_table, e: kayan_entity) -> u64 = {
    if (t*.count == t*.capacity) {
        kayan_table_grow(r, w, t);
    }
    row: u64 = t*.count;
    t*.count += 1;
    t*.entities[row] = e;
    for (id: u32 = 0; id < w*.component_count; id += 1) {
        if (kayan_table_has(t, id)) {
            kayan_column_zero_row(t*.columns[id]&, row);
        }
    }
    return row;
}
```

Removing a row is 1.4's swap-remove, for every column:

```rin
kayan_table_remove_row: proc(w: *kayan_world in level, t: *kayan_table, row: u64) -> void = {
    last: u64 = t*.count - 1;
    if (row != last) {
        for (id: u32 = 0; id < w*.component_count; id += 1) {
            if (kayan_table_has(t, id)) {
                kayan_column_copy_row(t*.columns[id]&, row, last);
            }
        }
        moved: kayan_entity = t*.entities[last];
        t*.entities[row] = moved;
        vec<kayan_slot>at(w*.slots, cast(moved.index, u64))*.row = cast(row, u32);
    }
    t*.count = last;
}
```

Compare it with 1.4's `kayan_despawn`: the same moves and the same slot fix,
but over columns of bytes instead of named arrays. This proc works for any
table that will ever exist.

Compare the two signatures, too. Adding a row can allocate, so it takes
`r: region level`. Removing one can't, so it doesn't. Whether a proc can allocate
is written where you can see it.

## Step 3: the typed view of a table

```rin
kayan_slice: proc<T>(t: *kayan_table in level) -> []T in level = {
    id: u32 = kayan_id_of<T>();
    if (!kayan_table_has(t, id)) {
        printfmt("kayan: the table has no column for component {}\n", id);
        exit(1);
    }
    return kayan_column_slice<T>(t*.columns[id]&, t*.count);
}
```

`kayan_slice<position>(t)` is the table's position column as a `[]position`,
cut to the rows in use. Systems will live on this in Part 3: get the slices,
loop over rows. Notice that this proc is checked: `unsafe { }` is still only in
the two column procs from 2.2, and nothing above them needs it.

## Step 4: the world

The world moves off `main`'s stack and into the region, with everything it holds:

```rin
kayan_world: struct = {
    infos: [64]option<*const reflect in permanent>;
    component_count: u32;
    slots: *vec<kayan_slot> in level;
    free: *vec<u32> in level;
    live: u64;
    table: kayan_table;
}
```

The registry from 2.1, the slots and free list from Part 1 (as `vec`s now, so
the 8-entity limit is gone), and one table.

`*vec<kayan_slot> in level` is a plain pointer, not an `option`: it may not be
null, ever, so every proc can use it without a test. The price is that the world
can't exist for a moment without its vecs, so it's made whole, in one expression:

```rin
kayan_world_make: proc(r: region level) -> *kayan_world in level = {
    return new<kayan_world>(r, {
        .slots = vec<kayan_slot>make(r, 8),
        .free = vec<u32>make(r, 8),
    });
}
```

Leave one out and it doesn't compile:

```
type error: field 'free' is left zero, and it holds a pointer that may not be null; set it here, or make it 'option<*T>'
```

From here on, every proc takes the world as `*kayan_world in level`. It lives
there, so a pointer to its table is a level pointer too, good for as long as the
level is.

Spawning is Part 1's spawn with the row coming from the table:

```rin
    row: u64 = kayan_table_add_row(r, w, w*.table&, e);
    vec<kayan_slot>at(w*.slots, cast(e.index, u64))*.row = cast(row, u32);
    w*.live += 1;
    return e;
```

and despawning is Part 1's despawn calling `kayan_table_remove_row`.

Look at the order in that sample. The pointer into `slots` is taken after adding
the row, and used at once. `slots` is a vec, and a vec's items move when it
grows, so a pointer into one is only good until the next thing that might grow
it. Adding a row doesn't touch `slots` here, but the habit costs nothing, and in
2.4 the checker will insist on it.

## Step 5: writing a new entity's data

There's no typed `get` or `set` yet (that's 2.5), so the program finds the
row and writes through the column slices:

```rin
            row: u64 = kayan_row(w, drones[i]);
            ps: []position in level = kayan_slice<position>(w*.table&);
            vs: []velocity in level = kayan_slice<velocity>(w*.table&);
            hs: []health in level = kayan_slice<health>(w*.table&);
            ps[row] = { .at = { .x = 10.0 * cast(i, f32), .y = 0.0 } };
```

## Run it

```
spawned 6 drones into one table; it grew from 4 rows to 8
    6 rows, room for 8
    row 0  0:1  position ( 0.00,  0.00)  health 100
...
despawn 0:1 and 3:1
    4 rows, room for 8
    row 0  5:1  position (50.00,  0.00)  health 100
    row 1  1:1  position (10.00,  0.00)  health 100
    row 2  2:1  position (20.00,  0.00)  health 100
    row 3  4:1  position (40.00,  0.00)  health 100
spawn 3:2: a reused number, the next row, zeroed except what we set
...
kayan_verify: 0 problems
```

Row 0 went to `5:1` (the last row moved into the hole), then row 3 went to
`4:1` the same way. Every column moved together, and the slots followed.
