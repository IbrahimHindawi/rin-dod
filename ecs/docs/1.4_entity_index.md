# 1.4 The entity index

`ecs/src/1.entities/1.4.entity_index/entity_index.rin`

**In the dojo:** [2. swap-remove and the back-reference](../../dojo/2.swap_remove/README.md), [3. the slot map](../../dojo/3.slot_map/README.md), each on its own, to watch and to practise.

Handles fixed identity. Two costs from 1.1 remain: every array is as long as
the most entities, and every system walks all of it, skipping holes. This
chapter **packs** the data: live entities in rows 0 to `count - 1`, no holes,
so a system is a straight loop over the rows. That's the stream lesson 1
measured as the fast case.

Packing has a consequence that the rest of the course is built around:
**an entity's data no longer sits at its number, and it moves.**

To keep this chapter about the index, every entity is the same kind of thing:
a particle with a position and a velocity. Part 2 brings back different kinds,
each packed in a table of its own.

## Step 1: two halves

```rin
kayan_slot: struct = {
    generation: u32;
    row: u32;
}
```

```rin
kayan_world: struct = {
    slot_count: u32;
    slots: [8]kayan_slot;
    free: [8]u32;
    free_count: u32;

    count: u32;
    entities: [8]kayan_entity;
    positions: [8]vec2;
    velocities: [8]vec2;
}
```

The world now has two halves:

- **The slots**, indexed by the entity's number. A number never moves, so this
  is where a handle looks first. A slot holds the generation from 1.3, and now
  also **the row** the entity's data is in.
- **The rows**, packed. `count` of them, each with its components side by side
  in the arrays, and `entities[row]` saying which entity owns the row.

The two point at each other: slot to row, row to entity. That two-way link is
called the **entity index**.

## Step 2: spawning appends a row

```rin
    row: u32 = w*.count;
    w*.count += 1;
    w*.entities[row] = e;
    w*.positions[row] = p;
    w*.velocities[row] = v;
    w*.slots[e.index].row = row;
    return e;
```

The number comes from the free list or the end, exactly as in 1.3. The data
goes in the next row, which is always the end of the packed rows. The slot
records where.

## Step 3: despawning swap-removes

To keep the rows packed, a hole can't be left behind. The last row moves into
it, called **swap-remove**:

```rin
kayan_despawn: proc(w: *kayan_world, e: kayan_entity) -> kayan_status = {
    if (!kayan_alive(w, e)) {
        return kayan_status.dead;
    }
    row: u32 = w*.slots[e.index].row;
    last: u32 = w*.count - 1;
    if (row != last) {
        moved: kayan_entity = w*.entities[last];
        w*.entities[row] = moved;
        w*.positions[row] = w*.positions[last];
        w*.velocities[row] = w*.velocities[last];
        w*.slots[moved.index].row = row;
    }
    w*.count -= 1;
    w*.slots[e.index].generation += 1;
    w*.free[w*.free_count] = e.index;
    w*.free_count += 1;
    return kayan_status.ok;
}
```

The line that matters is this one:

```rin
        w*.slots[moved.index].row = row;
```

The entity that owned the last row now lives somewhere else, and its slot must
say so. `entities[last]` is how we know *whose* slot to fix: without that
column, a moved row would be anonymous. Forget the line and that entity's
handle still finds a row, just the wrong one, and nothing crashes.

Swap-remove costs one row copy, however many rows there are. Removing by
shifting everything after the hole down would keep the order, but cost a copy
of every later row. ECSs don't promise order, so they take the cheap one.

## Step 4: reading through the index

```rin
get_position: proc(w: *kayan_world, e: kayan_entity) -> *vec2 = {
    if (!kayan_alive(w, e)) {
        return null;
    }
    return w*.positions[w*.slots[e.index].row]&;
}
```

Handle to slot to row. That's one extra lookup compared with 1.3, and it's
the price of packing. Systems don't pay it, because they don't go through
handles:

```rin
movement_system: proc(w: *kayan_world, dt: f32) -> void = {
    for (row: u32 = 0; row < w*.count; row += 1) {
        w*.positions[row].x += w*.velocities[row].x * dt;
        w*.positions[row].y += w*.velocities[row].y * dt;
    }
}
```

No flags, no holes, no handles. Every row is a live particle. This is the loop
the rest of the course works to keep.

## Step 5: checking the invariant

Rows move all the time, and one missed slot update corrupts the world
silently. So the world can check itself:

```rin
kayan_verify: proc(w: *kayan_world) -> u32 = {
    problems: u32 = 0;
    for (row: u32 = 0; row < w*.count; row += 1) {
        e: kayan_entity = w*.entities[row];
        if (!kayan_alive(w, e)) {
            printfmt("kayan_verify: row {} holds dead entity {}:{}\n", row, e.index, e.generation);
            problems += 1;
        } else if (w*.slots[e.index].row != row) {
            printfmt("kayan_verify: {}:{} is in row {}, its slot says row {}\n",
                e.index, e.generation, row, w*.slots[e.index].row);
            problems += 1;
        }
    }
    live: u32 = w*.slot_count - w*.free_count;
    if (live != w*.count) {
        printfmt("kayan_verify: {} rows, {} live entities\n", w*.count, live);
        problems += 1;
    }
    return problems;
}
```

**The invariant: every row belongs to a live entity whose slot points back
at that row, and there are as many rows as live entities.** Every structural
change in this course has to keep it true. When something goes wrong later,
run `kayan_verify` first.

## Run it

```
spawned 5 particles
    row 0  0:1  position ( 0.00,  0.00)
    row 1  1:1  position ( 1.00,  0.00)
    ...
    row 4  4:1  position ( 4.00,  0.00)
    slots:  0 -> row 0  1 -> row 1  2 -> row 2  3 -> row 3  4 -> row 4
despawn 1:1, in row 1: the last row moves into the hole
    row 0  0:1  position ( 0.00,  0.00)
    row 1  4:1  position ( 4.00,  0.00)
    row 2  2:1  position ( 2.00,  0.00)
    row 3  3:1  position ( 3.00,  0.00)
    slots:  0 -> row 0  1 free  2 -> row 2  3 -> row 3  4 -> row 1
despawn 4:1, which the last despawn moved: its handle still finds it
...
kayan_verify: 0 problems
```

Follow `4:1`: it starts in row 4, moves to row 1 when `1:1` is removed, and its
handle still finds it there because its slot was updated.

## Part 1 in one picture

```
handle 4:1 ──> slots[4] { generation 1, row 1 } ──> rows[1] { owner 4:1, position, velocity }
```

- **Handles** never change: they're what the rest of the game keeps.
- **Slots** never move: one per number, holding the generation and the row.
- **Rows** move all the time, and stay packed so systems can stream them.

Part 2 keeps exactly this, and generalizes the one kind of row into tables,
one per combination of components.
