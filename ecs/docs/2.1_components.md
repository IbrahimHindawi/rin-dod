# 2.1 Components and signatures

`ecs/src/2.components/2.1.components/components.rin`

**In the dojo:** [6. bitsets](../../dojo/6.bitset/README.md), on its own, to watch and to practise.

Part 1 hard-coded its components: a `positions` array, a `velocities` array,
a flag for each. Adding a component meant editing the world, `kayan_spawn`,
`kayan_despawn` and every printer. Part 2 builds a world that works for
components it has never heard of. This chapter lays the ground with four ideas:

1. A component is a plain struct.
2. Each component type has an **id**, a small number fixed at compile time.
3. The world keeps a **registry**: per id, the component's size, alignment and
   name, which is all it needs to store bytes it doesn't understand.
4. A set of components is a **signature**: one bit per id in a `u64`.

There are no entities in this chapter. 2.3 puts the two halves together.

## Step 1: components are plain structs

```rin
position: struct = { at: vec2; }
velocity: struct = { per_second: vec2; }
health: struct = { points: f32; max: f32; }
damage: struct = { amount: f32; }
lifetime: struct = { seconds: f32; }
burning: struct = { per_second: f32; }
turret: struct = { cooldown: f32; timer: f32; }
```

No procs, no pointers to other entities, no idea that a world exists. That's
deliberate. Behaviour belongs to systems, and data that knows nothing can be
copied, moved and stored as raw bytes, which the world is about to do.

Why `position { at: vec2 }` rather than using `vec2` directly? Because a
component's *type* is how the world tells components apart. Position and
velocity are both two floats, but they're different things, and making them
different types is what lets you ask for one and not the other.

## Step 2: an id per component type

```rin
component: enum = {
    position,
    velocity,
    health,
    damage,
    lifetime,
    burning,
    turret,
}
```

The enum gives each component a number. Then one line per type connects the
type to its number:

```rin
component_of: proc<position>() -> component = { return component.position; }
component_of: proc<velocity>() -> component = { return component.velocity; }
```

Each line is a **specialization** of the generic proc `component_of<T>` for
one type. `component_of<health>()` is resolved by the compiler to
`component.health`. Nothing is looked up at run time; the id is a constant in
the generated code.

## Step 3: the world speaks ids, never types

The world can't be generic over component types. Which combinations exist is
only known while the game runs (the "untyped core" from our earlier
discussion). So the world works in ids and bits, and a small **typed layer**
translates:

```rin
kayan_bit: proc(id: u32) -> u64 = {
    return 1'u64 shl cast(id, u64);
}

// The typed layer: from a type to the id and bit the world works in.
kayan_id_of: proc<T>() -> u32 = {
    return cast(component_of<T>(), u32);
}

kayan_mask_of: proc<T>() -> u64 = {
    return kayan_bit(kayan_id_of<T>());
}
```

Game code says `kayan_mask_of<velocity>()`, and the world only ever sees
`2`, a bit.

## Step 4: the registry

To store a component as bytes, the world needs three facts about it: how many
bytes, what alignment, and a name for printing. rin's compiler already wrote
all three down. `position<>` is the **reflect record** for `position`, data the
compiler puts into the program. So the registry is an array of pointers to
reflect records, indexed by id:

```rin
kayan_world: struct = {
    infos: [64]*const reflect;
    component_count: u32;
}
```

```rin
kayan_register: proc(w: *kayan_world, id: u32, info: *const reflect) -> void = {
    if (id >= 64) {
        printfmt("kayan: component id {} is past the 64 a signature can hold\n", id);
        exit(1);
    }
    w*.infos[id] = info;
    if (id + 1 > w*.component_count) {
        w*.component_count = id + 1;
    }
}
```

```rin
register_components: proc(w: *kayan_world) -> void = {
    kayan_register(w, kayan_id_of<position>(), position<>&);
    kayan_register(w, kayan_id_of<velocity>(), velocity<>&);
```

Each line names the type twice, once for the id and once for the record. A
generic `kayan_register_type<T>` that took `T<>&` would be nicer, but rin
doesn't yet allow `T<>` on a generic parameter, so registration names each
type.

## Step 5: signatures

A set of components is a `u64` with a bit set per component in the set. What
a thing *is* is a signature:

```rin
    drone: u64 = kayan_mask_of<position>() | kayan_mask_of<velocity>() | kayan_mask_of<health>();
```

Every question you'd ask about sets is a bit operation:

```rin
kayan_contains: proc(signature: u64, wanted: u64) -> b32 = {
    return (signature & wanted) == wanted;
}
```

"Does this drone have what movement wants?" is `kayan_contains(drone,
moves)`, one AND and one compare. Adding a component is `|`, and removing one
is `& ~`:

```rin
    put_out: u64 = burning_drone & ~kayan_mask_of<burning>();
```

64 bits means at most 64 component types per world, which is plenty for
learning and for most games. Larger ECSs use wider bitsets or sorted id
lists; the idea is the same.

## Run it

```
the registry: 7 components
    id  name       size  align
     0  position      8      4
     1  velocity      8      4
     2  health        8      4
     3  damage        4      4
     4  lifetime      4      4
     5  burning       4      4
     6  turret        8      4
signatures, one bit per component, highest id first:
    drone          0000111  {position velocity health}
    bullet         0011011  {position velocity damage lifetime}
    turret         1000001  {position turret}
    burning drone  0100111  {position velocity health burning}
movement wants {position velocity}:
    drone yes, bullet yes, turret no, burning drone yes
a burning drone with burning removed is a drone again: yes
```

Read the bits as a table: each column is a component, each row a kind of
thing. That table is the next three chapters. Each distinct row will become
a table of its own.
