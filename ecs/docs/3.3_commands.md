# 3.3 Commands

`ecs/src/3.systems/3.3.commands/commands.rin`

**In the dojo:** [5. a command buffer](../../dojo/5.commands/README.md), [7. an arena](../../dojo/7.arena/README.md), each on its own, to watch and to practise.

3.2's systems change values, never structure, so bullets whose time ran out
stay in the world. The obvious fix is to despawn them from inside the system.
It's wrong, and seeing exactly why is most of this chapter.

## Step 1: the bug

```rin
expire_now_system: proc(it: *kayan_iter) -> void = {
    t: *kayan_table in level = it*.table;
    for (row: u64 = 0; row < t*.count; row += 1) {
        ls: []lifetime = kayan_slice<lifetime>(t);
        es: []kayan_entity = kayan_entities(t);
        if (ls[row].seconds <= 0.0) {
            _ = kayan_despawn(it*.world, es[row]);
        }
    }
}
```

Four bullets, three of them out of time:

```
1. an expire system that despawns as it goes
    lifetimes:  0:1 0.00  1:1 1.00  2:1 0.00  3:1 0.00
after one frame:
    lifetimes:  3:1 0.00  1:1 1.00
kayan_verify: 0 problems. The world is fine; the loop missed one.
```

Row by row:

```
row 0: 0:1 is out of time. Despawn: the last row, 3:1, moves into row 0.
row 1: 1:1 has time left.
row 2: 2:1 is out of time. Despawn: it's the last row, so nothing moves.
row 3: the table has 2 rows now. Stop.
```

`3:1` moved into row 0, which the loop had already passed, so it was never
looked at. The world is perfectly consistent (`kayan_verify` agrees). The
*loop* is what's wrong: a despawn swap-removes from the table the loop is
walking.

The checker lets this through, and it isn't wrong to. The slices are taken again
each time round, every read is in bounds, and nothing touches bad memory. A
missed row is a logic bug, and that's the kind of bug a loop over indices leaves
you with. No memory checker is coming to help here. The fix has to be a design.

Walking backwards fixes this case (lesson 2 does it), because the row that
moves in has already been looked at. But it doesn't fix the general problem:

- **Adding or removing** a component moves the entity to *another* table. If
  the query matches that table too and visits it later, the entity is
  processed twice.
- That move adds a row, and if the destination table is full, its columns grow
  and move. A slice into that table is then looking at the old block, which the
  region still owns, so nothing crashes and every write through it is lost. This
  is 2.5's bug, from inside a loop. A slice is a borrow, and the checker ends a
  borrow when it can see the world changing beneath it. Inside a system it can't
  always: the table and the world both arrive through `it`, and it has no way to
  connect them. So the region keeps this safe, and something else has to keep it
  right.
- One system's despawn can land in a table **another** system is halfway
  through, if a system despawns entities it found through a second query.

## Step 2: record now, apply later

So a system doesn't change structure. It records a **command** saying what
should change, and the world applies every command after the frame's last
system:

```
during the frame   values change; tables, rows and pointers do not
after the frame    spawns, despawns, adds and removes, in order
```

```rin
kayan_command_kind: enum = {
    spawn,
    despawn,
    add,
    remove,
}

kayan_command: struct = {
    kind: kayan_command_kind;
    entity: kayan_entity;
    spawn: u32;
    id: u32;
    signature: u64;
    value: []u8 in frame;
}
```

A command names the entity, and for an add or remove the component id. An
add carries its value as bytes. The bytes, and the list of commands, are only
needed until the end of the frame, so they get memory that ends with the frame.
That's a second region:

```rin
level: region;
frame: region in level;
```

`in level` says `frame` opens and ends inside `level`. So memory in `frame` may
point into `level`, since `level` will still be there. The other way round is
refused, and that's what makes this shape safe. Try to keep a command in the
world, and it doesn't compile:

```
type error: this points into region 'frame', which may end before the memory in region 'level' that holds it
```

So **no command can outlive its frame**, by construction, and no one has to
remember to check. The buffer is the commands and the arena their values are
copied into:

```rin
kayan_commands: struct = {
    heap: *kayan_heap in frame;
    list: *vec<kayan_command> in frame;
}

kayan_commands_make: proc(r: region frame) -> *kayan_commands in frame = {
    return new<kayan_commands>(r, { .heap = kayan_heap_make(r), .list = vec<kayan_command>make(r, 16) });
}
```

and a frame opens the region, makes the buffer, runs, and ends:

```rin
run_frame: proc(w: *kayan_world in level, systems: *const vec<*kayan_scheduled in level>, dt: f32) -> void = {
    frame: region = {
        kayan_progress(w, systems, dt, kayan_commands_make(frame));
    }
}
```

There's no line that drops the commands. The end of that block is it, whatever
they were. A loop variable can't be called `frame` any more, either, now that it
names a region, so these chapters count `frame_no`.

Systems reach the buffer through their iterator, which gains two fields:

```rin
kayan_iter: struct = {
    world: *kayan_world in level;
    table: *kayan_table in level;
    dt: f32;
    commands: *kayan_commands in frame;
    ctx: option<*kayan_query in level>;
}
```

## Step 3: recording

The typed procs a system calls copy the value into the frame's arena and
append a command:

```rin
kayan_defer_value: proc<T>(h: *kayan_heap in frame, value: T) -> []u8 in frame = {
    unsafe {
        data: ^u8 = cast(memops_arena_push(h*.arena[0]&, sizeof(T), alignof(T)), ^u8);
        memcpy(data, value&, sizeof(T));
        return cast(data[0..sizeof(T)], []u8 in frame);
    }
}
```

That's the command buffer's one trusted proc, because a value's bytes are a cast.
Its signature says what matters: the bytes are `in frame`, so they get the same
protection as the command that holds them.

```rin
kayan_defer_add: proc<T>(cmds: *kayan_commands, e: kayan_entity, value: T) -> void = {
    _ = kayan_defer(cmds, { .kind = kayan_command_kind.add, .entity = e, .id = kayan_id_of<T>(),
        .value = kayan_defer_value<T>(cmds*.heap, value) });
}
```

The fixed expire system is the broken one with one word changed:

```rin
expire_system: proc(it: *kayan_iter) -> void = {
    ls: []lifetime = kayan_slice<lifetime>(it*.table);
    es: []kayan_entity = kayan_entities(it*.table);
    for (row: u64 = 0; row < es.length; row += 1) {
        if (ls[row].seconds <= 0.0) {
            kayan_defer_despawn(it*.commands, es[row]);
        }
    }
}
```

Now the table doesn't change while the loop runs, so the loop can take the
entities as a slice up front, like any other column.

## Step 4: applying, by id

Commands hold bytes and ids, not types. So applying an add needs 2.6's add
*by id*:

```rin
kayan_add_id: proc(w: *kayan_world, e: kayan_entity, id: u32, value: []const u8) -> kayan_status = {
    if (!kayan_alive(w, e)) {
        return kayan_status.dead;
    }
    from: u32 = vec<kayan_slot>at(w*.slots, cast(e.index, u64))*.table;
    if (!kayan_table_has(kayan_table_at(w, from), id)) {
        kayan_move(w, e, kayan_table_with(w, from, id));
    }
    bytes: []u8 = kayan_get_bytes(w, e, id);
    if (value.length != bytes.length) {
        printfmt("kayan: a {}-byte value for a component of {} bytes\n", value.length, bytes.length);
        exit(1);
    }
    for (i: u64 = 0; i < bytes.length; i += 1) {
        bytes[i] = value[i];
    }
    return kayan_status.ok;
}
```

It's the same move-then-write as before, with the write a checked loop over the
value's bytes. Once that exists, the typed `kayan_remove<T>` from 2.6 shrinks to a
one-line wrapper. That's the pattern from the start of the course: byte fiddling
written once, a type-safe generic layer on top.

```rin
kayan_remove: proc<T>(w: *kayan_world, e: kayan_entity) -> kayan_status = {
    return kayan_remove_id(w, e, kayan_id_of<T>());
}
```

`kayan_add<T>` keeps its 2.6 body instead of calling this one. To go through
`kayan_add_id` it would have to turn its `T` into bytes, and that's a cast, which
would make it another trusted proc. It moves the entity and calls `kayan_set<T>`
instead, and stays checked. The boundary between typed and untyped code is
somewhere you want as few crossings as possible.

`kayan_flush` walks the list in order and applies each command. It's called
at the end of `kayan_progress`:

```rin
    kayan_flush(w, cmds);
}
```

## Step 5: commands that arrive too late

By the time a command is applied, its entity may be gone. The usual case is
two systems both asking to despawn the same thing. Applying in order handles
that for free: the first despawn works, and the second finds a dead handle.
Part 1's generations make that check one comparison:

```rin
        if (status == kayan_status.ok) {
            w*.applied += 1;
        } else {
            w*.skipped += 1;
        }
```

## Step 6: spawning from a system

A turret firing is a spawn in the middle of a frame. The new entity doesn't
exist until the commands are applied, so there's no handle to give its
components to. `kayan_defer_spawn` returns a **pending** spawn instead: the
spawn command's place in the list. Components are given to that:

```rin
            shot: kayan_pending = kayan_defer_spawn(it*.commands, bullet_signature());
            kayan_pending_set<position>(it*.commands, shot, ps[row]);
            kayan_pending_set<velocity>(it*.commands, shot, { .per_second = { .x = 8.0, .y = 0.0 } });
            kayan_pending_set<damage>(it*.commands, shot, { .amount = 25.0 });
            kayan_pending_set<lifetime>(it*.commands, shot, { .seconds = 2.0 });
```

When the flush reaches the spawn, it makes the entity and writes the handle
into the command. The adds after it look the handle up there. The bullet is
spawned with its full signature, so the adds land in the table it's already
in: no moves. And it doesn't move until the next frame, because no system
ran over it this one.

The flush allocates in `level`, deep inside a frame, with no `level` in sight.
This is why 3.1 had the world remember its region.

## Step 7: a system with two queries

A bullet that reaches a target damages it. The hit system walks the bullets
(its own query) and, for each, the targets (a second query). It reaches the
second query through a new field, `ctx`, which kayan passes through untouched:

```rin
    targets: option<*kayan_query in level> = it*.ctx;
    if (!targets) {
        return;
    }
```

`ctx` is a typed pointer rather than a `*void`, because the checker has to know
what it points at. A system with no second query gets `null`, so the ones that use
it test it first.

The damage is a value, so it's written now. The bullet's despawn is
structure, so it's recorded. Walking a second query in the middle of a frame
is safe *because* of commands: no table is made and no column moves until the
frame is over. The slices in this system stay true for the whole frame, and
that's the guarantee no checker gave us: the design did.

## Run it

```
2. an expire system that records despawns
    lifetimes:  0:1 0.00  1:1 1.00  2:1 0.00  3:1 0.00
    despawn 0:1
    despawn 2:1
    despawn 3:1
after one frame:
    lifetimes:  1:1 1.00
```

All three. Then the turret, with two targets 0.25 apart in its line of fire
and a third out of it:

```
3. a turret, two targets in its line of fire, one out of it
frame 1
    spawn {position velocity damage lifetime} -> 4:1
frame 2
frame 3
    spawn {position velocity damage lifetime} -> 5:1
frame 4
    despawn 4:1
    despawn 4:1: skipped, dead
frame 5
    spawn {position velocity damage lifetime} -> 4:2
...
health: 1:1 50, 2:1 50, 3:1 100
commands applied: 17, skipped: 2
```

In frame 4, bullet `4:1` is close enough to both targets. Both lose 25, and
both hits record a despawn. The first applies; the second finds `4:1`
already dead and is skipped. In frame 5 the next bullet gets number 4 back
with generation 2: Part 1, working.

17 commands, for three bullets and two despawns: each spawn is five, the
spawn and its four components.

## Try

1. In `expire_now_system`, take `ls` and `es` once, before the loop, and loop to
   `ls.length` instead of `t*.count`. It still compiles, and now all three get
   despawned. Work out why. (Hint: what's in the rows past the end of the table?)
   Is that loop correct?
2. Write a system that adds `burning` directly (not deferred) to every target
   it walks. Count how many times it visits each entity.
3. Flush after *each* system instead of after the frame. You'll have to empty the
   list after each flush, with `vec<kayan_command>clear(cmds*.list)`, since it's
   no longer the region's end that lets the commands go. What does that change
   about what later systems see? (flecs calls these *sync points*.)
4. Add a field `kept: option<*kayan_commands in frame>;` to `kayan_world`, and
   compile. Which rule did you just run into, and what bug is it saving you from?
