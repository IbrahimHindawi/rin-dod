# 3.2 Systems

`ecs/src/3.systems/3.2.systems/systems.rin`

**In the dojo:** [13. a dispatch table](../../dojo/13.dispatch/README.md), on its own, to watch and to practise.

3.1's movement loop had the shape of every system: bring a query up to date,
then for each of its tables take the columns as slices and loop over the rows.
This chapter names that shape and splits it in two:

- **the kernel**: a plain loop over plain slices. It knows nothing about
  tables, entities or worlds. This is lessons 1 to 7: `noalias`, streaming,
  vectorization.
- **the system**: a query, plus a small proc kayan calls on each table the
  query matches. It takes the table's columns and calls the kernel.

A frame runs the systems in order, each over all of its tables. The order is
the **schedule**, and it's written down once, as data.

## Step 1: the kernels

```rin
integrate: proc[unsafe](ps: noalias []position, vs: []const velocity, dt: f32) -> void = {
    for (i: u64 = 0; i < ps.length; i += 1) {
        ps[i].at.x += vs[i].per_second.x * dt;
        ps[i].at.y += vs[i].per_second.y * dt;
    }
}
```

That's the whole thing, and it's the code you'd want to write if there were
no ECS at all. Kernels are where you profile, read assembly and reach for
SIMD (the lessons). Everything else in this course exists to hand them the
right slices. `burn` and `age` look the same.

Why `proc[unsafe]`, on a loop this innocent? Because of one word. `noalias` tells
the C optimiser these slices don't overlap, and that's a promise the checker has
no way to keep. It wants you to mark that plainly:

```
type error: noalias is a promise to the C optimiser that the checker cannot keep: it belongs on a 'proc[unsafe]'
```

The body is as ordinary as it looks, bounds checks included, and overlap is still
tested on the way in unless you turn the checks off. All that `[unsafe]` means here
is that the performance promise is yours to keep.

## Step 2: what a system gets

```rin
kayan_iter: struct = {
    world: *kayan_world in level;
    table: *kayan_table in level;
    dt: f32;
}

kayan_system_proc: alias = *proc(it: *kayan_iter) -> void;
```

One struct instead of three parameters. It's the same idea as flecs'
`ecs_iter_t`, and it has two practical reasons. Adding to it later (3.3 adds
two fields) changes no system's signature. And a system that uses only the
table still uses its one parameter. rin compiles to C with
`-Wextra -Werror`, and an unused parameter is an error there. Both pointers name
their region, so the struct can be made anywhere `level` is open.

The system itself is the adapter:

```rin
move_system: proc(it: *kayan_iter) -> void = {
    unsafe { integrate(kayan_slice<position>(it*.table), kayan_slice<velocity>(it*.table), it*.dt); }
}
```

Columns out, kernel in. No loop here: the kernel has it.

This is where you keep the kernel's promise, so it's where the `unsafe { }` goes.
It's easy to keep: a position column and a velocity column are different
allocations, so they can't overlap. It's the only line in the system, and it says
what you're vouching for.

## Step 3: a system is data

A system is a name, a proc, a query, and the counts of the work it's done. Only
the first two never change, and that turns out to be the seam the checker needs,
so a system comes in two halves.

The code:

```rin
kayan_system: struct = {
    name: ^const char;
    run: kayan_system_proc;
}

kayan_system_make: proc(r: region level, name: ^const char, run: kayan_system_proc) -> *kayan_system in level = {
    unsafe {
        s: *kayan_system in level = cast(memops_arena_push_zero(r, sizeof(kayan_system), alignof(kayan_system)), *kayan_system in level);
        s*.name = name;
        s*.run = run;
        return s;
    }
}
```

A C string and a proc pointer are both pointers without a region, so the checker
can't place them. It won't let `new` make a struct holding them, and it says what
it wants instead:

```
type error: a value made by new holds 'kayan_system' by value, and it carries a pointer whose region the checker cannot see; safe code keeps such a value through a pointer into a region, '*kayan_system in R', made by a proc of its own; if a field of it is stored from two regions, write its region on the field
```

So a small trusted proc makes it, once, and everyone else holds a pointer. Nothing
is lost, because nothing here changes either field after that.

The data:

```rin
kayan_scheduled: struct = {
    system: *kayan_system in level;
    query: kayan_query;
    tables: u64;
    rows: u64;
}
```

Everything that changes as the frames go is here, as plain checked data. `tables`
and `rows` count the work, for the output. The schedule is a list of these:

```rin
        systems: *vec<*kayan_scheduled in level> in level = vec<*kayan_scheduled in level>make(level, 3);
        kayan_schedule_add(level, systems, "burn", kayan_mask_of<health>() | kayan_mask_of<burning>(), 0, burn_system);
        kayan_schedule_add(level, systems, "age", kayan_mask_of<lifetime>(), 0, age_system);
        kayan_schedule_add(level, systems, "move", kayan_mask_of<position>() | kayan_mask_of<velocity>(), 0, move_system);
```

It's a vec of pointers for the same reason as `w.tables` in 2.4. Each entry is its
own allocation, so a pointer to one is a pointer into `level`, which never goes
stale.

## Step 4: a frame

```rin
kayan_progress: proc(w: *kayan_world in level, systems: *const vec<*kayan_scheduled in level>, dt: f32) -> void = {
    for (s: u64 = 0; s < systems*.length; s += 1) {
        sys: *kayan_scheduled in level = kayan_scheduled_at(systems, s);
        kayan_query_update(w, sys*.query&);
        for (i: u64 = 0; i < sys*.query.tables*.length; i += 1) {
            it: kayan_iter = { .world = w, .table = kayan_query_table(w, sys*.query&, i), .dt = dt };
            if (it.table*.count > 0) {
                sys*.tables += 1;
                sys*.rows += it.table*.count;
                sys*.system*.run(it&);
            }
        }
    }
}
```

`kayan_progress` is flecs' name for the same thing. For each system in order,
for each of its tables, one call. The game loop becomes:

```rin
        for (frame: u32 = 1; frame <= 8; frame += 1) {
            kayan_progress(w, systems, dt);
```

## Order is data flow

Systems run one after another, never interleaved, and each sees everything
the earlier ones wrote this frame. So the order is a statement about data: a
system that **reads** what another **writes** runs after it. Move before
collide means bullets hit where they are now, not where they were. Damage
before death means a drone dies in the frame its health hits zero, not the
next. 3.4's schedule has nine systems, and each position in it is one of
these decisions.

Bigger engines go further. Each system declares what it reads and writes,
and the scheduler uses that to run systems that don't conflict at the same
time, on other threads. Underneath, the order is still a list like this one.

## Run it

```
the schedule, run in this order every frame:
burn: all {health burning}, none {}; tables: 1, entities: 1
    table 2 {position velocity health burning}: 2:1
age: all {lifetime}, none {}; tables: 1, entities: 3
    table 3 {position velocity damage lifetime}: 4:1 5:1 6:1
move: all {position velocity}, none {}; tables: 3, entities: 6
    table 1 {position velocity health}: 1:1 3:1
    table 2 {position velocity health burning}: 2:1
    table 3 {position velocity damage lifetime}: 4:1 5:1 6:1
...
after frame 8, 2.00 seconds:
    0:1 at ( 0.00,  0.00)
    1:1 at (18.00,  4.00)  health 100
    3:1 at (26.00, -4.00)  health 100
    2:1 at (22.00,  0.00)  health 84, burning
    4:1 at (17.00,  0.00)  lifetime -1.50
    5:1 at (17.00,  4.00)  lifetime -1.00
    6:1 at (17.00, -4.00)  lifetime -0.50

8 frames, one call per table per frame:
    burn called  8 times, over  8 rows
    age  called  8 times, over 24 rows
    move called 24 times, over 48 rows
3 bullets are out of time and still in the world
```

`move` made 24 calls in 8 frames, three tables a frame, and each call is one
tight loop. Call overhead is per table, never per entity.

And the last line is the cliffhanger. Each bullet's lifetime ran out, and
nothing removed it, because a system in this chapter changes values, never
structure. Despawning from inside a system looks like a one-line fix. It
isn't, and 3.3 shows why.
