# 2.5 Typed access

`ecs/src/2.components/2.5.typed_access/typed_access.rin`

**In the dojo:** [4. a type-erased column](../../dojo/4.column/README.md), [8. index, not pointer](../../dojo/8.index/README.md), each on its own, to watch and to practise.

The world stores any component in any combination, as bytes. Game code
should never see the bytes. This chapter adds the **typed layer** on top:

```
kayan_get<position>(w, e)          -> option<*position in level>: null if missing
kayan_has<velocity>(w, e)          -> b32
kayan_set<health>(w, e, value)     -> ok, dead, or missing
```

Each is a few lines that turn the type into an id, find the entity's table
and row through its slot, and hand the row back as a `T`. The byte-level core
underneath doesn't change at all. This is the split: a small unsafe core of byte
fiddling below, checked generic procs on top, each written once.

## Step 1: get

```rin
kayan_get: proc<T>(w: *kayan_world in level, e: kayan_entity) -> option<*T in level> = {
    if (!kayan_alive(w, e)) {
        return null;
    }
    slot: kayan_slot = vec<kayan_slot>at(w*.slots, cast(e.index, u64))*;
    t: *kayan_table in level = kayan_table_at(w, slot.table);
    if (!kayan_table_has(t, kayan_id_of<T>())) {
        return null;
    }
    rows: []T in level = kayan_slice<T>(t);
    return rows[cast(slot.row, u64)]&;
}
```

Handle, slot, table, row, typed view. It's the same path as 1.4's
`get_position`, for any component. Two ways to get `null`: the handle is dead,
or the entity has no `T`. The return type carries both facts the caller needs:
`option` means test it first, and `in level` means that once tested, it's memory
the program owns. The caller checks once and then has a real pointer.

## Step 2: has and set

```rin
kayan_has: proc<T>(w: *kayan_world in level, e: kayan_entity) -> b32 = {
    return (kayan_signature(w, e) & kayan_mask_of<T>()) != 0;
}
```

`kayan_has` doesn't touch the row at all. An entity's components are its
table's signature, one AND away.

```rin
kayan_set: proc<T>(w: *kayan_world in level, e: kayan_entity, value: T) -> kayan_status = {
    if (!kayan_alive(w, e)) {
        return kayan_status.dead;
    }
    p: option<*T in level> = kayan_get<T>(w, e);
    if (!p) {
        return kayan_status.missing;
    }
    p* = value;
    return kayan_status.ok;
}
```

`kayan_set` writes a component the entity already has. Giving it a component
it *doesn't* have changes which table it belongs in, and that's 2.6. So the
status gains a third value:

```rin
kayan_status: enum[must_use] = {
    ok,
    dead,
    missing,
}
```

## Step 3: building things

With `kayan_set`, game code builds entities with small procs. Engines call
these prefabs or archetype constructors:

```rin
spawn_drone: proc(r: region level, w: *kayan_world in level, x: f32, y: f32) -> kayan_entity = {
    e: kayan_entity = kayan_spawn(r, w, kayan_mask_of<position>() | kayan_mask_of<velocity>() | kayan_mask_of<health>());
    _ = kayan_set<position>(w, e, { .at = { .x = x, .y = y } });
    _ = kayan_set<velocity>(w, e, { .per_second = { .x = -1.0, .y = 0.0 } });
    _ = kayan_set<health>(w, e, { .points = 100.0, .max = 100.0 });
    return e;
}
```

The `_ =` says "I know this returns a status and I'm ignoring it on
purpose". Here that's safe: the entity was just spawned with exactly these
components.

Reading and changing is `kayan_get`, and a test:

```rin
        h: option<*health in level> = kayan_get<health>(w, a);
        if (h) {
            h*.points -= 25.0;
        }
```

## Step 4: keep handles, borrow pointers

The pointer `kayan_get` returns points into a column. 2.2 showed what columns
do when their table fills up: they move. So a pointer is good **until the next
structural change**: a spawn, a despawn, or (from 2.6) an add or remove. The
program proves it:

```rin
        kept: option<*health in level> = kayan_get<health>(w, a);
        for (i: u32 = 0; i < 8; i += 1) {
            _ = spawn_drone(level, w, 40.0 + cast(i, f32), 0.0);
        }
        if (kept) {
            kept*.points = 1.0;
        }
```

```
kept a pointer to 0:1's health, spawned 8 drones (the table grew), wrote 1 through it:
    0:1 at (20.00,  5.00), health 75
    the write went to the column's old block; the handle still finds the real one
```

The health is still 75. The write landed in the column's old block, which the
region still owns, so nothing crashes and no sanitizer complains. It's just
lost. Hence the rule every ECS has in some form:

**Keep handles. Borrow pointers: get, use, forget.**

It's worth being exact about what the checker did here, because this is the line
between what regions give you and what they don't. It lets the program through,
because `in level` asks for one thing: this pointer is memory in `level`, for as
long as `level` is open. That's true. The old block is still there. What the
pointer no longer is, is the component, and no amount of checking `level` can
tell you that. That's what a handle is for: the handle goes through the slot, so
it finds the row wherever it is now.

You can also ask for more. Write the pointer with no region, `option<*health>`,
and it's no longer a claim about memory. It's a borrow from `w`, and the checker
ends the borrow at the first call that may change `w`:

```
type error: 'kept' may be stale: 'w', which it was taken from, has been changed since; take it again
```

So a pointer you mean to use right away is best left without a region. Part 3's
systems write their column slices exactly that way.

## Run it

```
two drones and a bullet, built with kayan_set:
    0:1 at (20.00,  5.00), health 100
    1:1 at (30.00, -5.00), health 100
drone 0:1 is hit through kayan_get<health>:
    0:1 at (20.00,  5.00), health 75
the bullet has a velocity: yes; a health: no
kayan_get<health> on the bullet is null: yes
kayan_set<health> on the bullet: missing
despawned 1:1; kayan_set<health> on it now: dead
    1:1 is not a live drone
...
kayan_verify: 0 problems
```

## Try

1. Write `spawn_turret` and `spawn_bullet`-style procs for your own kinds of
   thing.
2. Move the `kept` pointer's `kayan_get` to *after* the spawning loop. Now the
   write sticks. Why?
3. Make `kayan_set` add the component when it's missing, instead of returning
   `missing`. What would it need from 2.6?
4. Change `kept` to an `option<*health>` and compile. Why is the program refused
   now, when the pointer goes to exactly the same place?
