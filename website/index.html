rin · data-oriented design · six lessons

rin-dod

From one array of structs to a small archetype entity component system, written in rin and checked against the output each program must print.

Data-oriented programming in rin, in six lessons: from one array of structs to a small archetype entity component system and a game that runs on it. The ECS is a rework of kayan: its core idea is kept and its rough edges are not. docs/0_from_kayan.md says which is which.

Every lesson is a standalone program in its own folder, laid out like rin-dx11: one source file that opens with what it teaches, and the output it must print beside it.

Lessons 1 to 3 are self-contained. Lesson 4 builds the world in includes/kayan.rin, and lessons 5 and 6 import it unchanged.

Build and run

Needs the rin compiler with noalias (rin e67175d or later; rin.exe from rin-windows-x64, through RIN_HOME or PATH), CMake, Ninja, clang-cl and the Windows SDK.

rin build
build\cmake\aos_vs_soa.exe

python tools/check.py builds every lesson with clang and warnings as errors, runs it, and compares what it prints with its .expected file. --sanitize adds AddressSanitizer and UBSan, --bless rewrites the expected files after a deliberate change, and a word filters the lessons:

python tools/check.py
python tools/check.py kayan --sanitize

The checker also works on Linux. There it relaxes -Wformat only: rin's printfmt and std print write %llu for u64, which is unsigned long on 64-bit Linux.

Reading it in a browser

Open website/index.html. It has every lesson's guide, its source with line numbers, and the output it must print, with an index on the left. It is generated from the files in this repository, so after changing a lesson or a guide run python tools/site.py to bring it up to date.

How to read it

Read each lesson's .rin file from the top. It opens with the problem it solves, and the code follows in the order it runs. Then run it and read the output against the code: every lesson prints what it does, step by step. The guides in docs/ give background that does not fit in a file header, and end with exercises.

Lesson 0 · review

From kayan

docs/0_from_kayan.md

kayan is a sketch of an archetype entity component system in C, about 200 lines in src/kayan.h, with haikal generating its containers. These lessons start from its idea and rebuild the rest. This page says what was kept, what was changed, and why, so the lessons can be read as a review of it as much as a rewrite.

What kayan does

Components are bits in an enum, positions = 1 << 0, velocities = 1 << 1 and so on. Each archetype is a C struct written by hand (A, B, C, D) that starts with an ArchetypeHeader and then holds one haikal Array_T per component. The header has a u64 signature and a Map_u64 from column name to the column's byte offset in the struct.

A query walks an array of void * pointing at the archetypes, reads each header, and tests (signature & want) == want. For a match it looks up "positions" and "velocities" in the offset map, adds the offsets to the struct's address, and runs the loop over the two columns.

Kept

  • An archetype is a struct of arrays. Each component is a contiguous column and every entity in the table has every column. That is the whole point, and kayan had it right from the start.
  • A signature is a u64 of component bits, and a query is the test (signature & all) == all. Lesson 3 adds a none mask beside it.
  • Arenas for all of it. Nothing in these lessons is freed one at a time.

Changed

  • One table type for every archetype (lesson 3). kayan needs a new C struct, a new signature line and new offset-map lines for every archetype. Here an archetype is data: a signature, and the world makes its table the first time something needs it (lesson 4).
  • Columns by component id, not by name (lesson 3). kayan hashes the strings "positions" and "velocities" on every query. Here a table's columns are an array indexed by component id, so finding one is an index. Names are kept for tools, through reflection (lesson 5).
  • The signature comes from the columns (lesson 3). In kayan they are written separately and can disagree. In D they do: it has positions and velocities columns, but its signature is health | damage | alive, so the movement query never visits it.
  • A row is added and removed in one place (lesson 2). kayan appends to each column at the call site, and keeps entity_count apart from the columns. For B and D it increments a's count instead of their own (kayan.h lines 142, 145, 168, 174), so A reports seven entities and the others report none. Nothing breaks only because the query loop happens to use the column's own length.
  • Entities have handles (lesson 4). kayan's entity id is the value of an archetype's entity_count before it is bumped: meant per table, in practice A's, as above. Nothing records where an entity lives, so there is no way to refer to one entity from elsewhere, to remove it, or to move it to another archetype. The lessons use an {index, generation} handle and a slot list that tracks each entity's table and row.
  • Entities move between archetypes (lesson 4). Adding or removing a component moves the entity to the matching table, copying the components both tables share.
  • Structural changes wait for the end of the frame (lesson 6), through a command buffer in a frame arena. kayan never changes structure while a query runs, but only because it never changes structure at all.
  • Reflection replaces hand-written tables (lessons 3 to 5). A component's size and alignment come from T<>, and so do the names a tool prints. The offset map goes away entirely.

Not carried over

  • **vec4s for positions.** kayan pads 3D vectors to 16 bytes, which suits SIMD loads. The lessons use vec2 and vec3 and plain loops, and leave vectorizing to the C compiler. noalias on the kernels' parameters, in lessons 1, 2, 3 and 6, lets it do that without run-time overlap checks. Lesson 1's exercises come back to vec4.
  • cglm and the haikal containers. rin's generics and std (vec<T>, hashmap<K, V>, slices) cover what they did.

Small things in kayan.h

  • The query's inner loop declares i32 i, shadowing the outer i (line 201).
  • Each lookup on lines 199 and 200 hashes and compares a string, once per column per archetype per query. That is cheap next to a large loop, but it is work that an array index does for nothing.

Lesson 1

AoS vs SoA

src/1.aos_vs_soa/aos_vs_soa.rin

src/1.aos_vs_soa/aos_vs_soa.rin

The same 262,144 particles, stored twice: once as an array of 68-byte particle structs, once as seven arrays, one per field. Sixty steps of movement run over each, and the program checks that both end with the same positions.

What the loop fetches

Memory reaches the CPU in 64-byte cache lines. A loop that reads 24 bytes of each 68-byte particle still pulls every byte of every line those particles sit in, so about two thirds of what movement fetches in the AoS loop is tint, age, lifetime, size and name. In the SoA loop the two arrays it reads are the only thing it fetches, and the hardware prefetcher sees two simple streams.

The program prints that arithmetic:

bytes fetched per step: 17825792     (AoS: 68 bytes x 262144)
bytes fetched per step: 6291456      (SoA: 24 bytes x 262144)

With --time it also prints how long each took. Release builds, best of five runs, on the 2.8 GHz Xeon these lessons were checked on:

gcc -O254.621.32.6x
gcc -O334.113.42.5x

clang -O345.326.31.7x

That machine has 33 MB of L3, so the 6 MB the SoA loop reads stays in cache between steps. The machine is shared; expect about 20 percent noise between runs. Debug numbers are not worth comparing: every positions[i] is bounds checked there.

For a Release build, set build_type to "Release" in build.rin and run rin build again. Release defines NDEBUG, which compiles the bounds checks out. Or compile the C that tools/check.py leaves in build/check/aos_vs_soa/ with -O2 -DNDEBUG.

The parameter list is the data

move_aos(ps: []particle, ...) says it needs particles. move_soa(positions: noalias []vec3, velocities: noalias []vec3, ...) says exactly which data it reads and writes. In lessons 2 and 3 every system is written the second way. In lesson 6 each system runs its own query, then works only on the columns it named.

Naming the columns is what lets a scheduler see that two systems touch different data, and it is what makes a system easy to test: hand it two small arrays.

noalias

As far as the C compiler can tell, two []vec3 slices could overlap. So before it works on several particles at once, it checks at run time that the two are apart, and keeps a one-at-a-time copy of the loop for when they are not. noalias on a parameter promises that, for the call, nothing else reaches the memory behind it. The check and the second copy go away.

The SoA loop without and with it, Release, ms:

buildwithout noaliaswith noalias
gcc -O331.713.4
gcc -O220.521.3
clang -O226.326.5
  • **gcc -O3** is where it shows. Without the promise, its checked vector loop was slower than not vectorizing at all (21 ms with -fno-tree-loop-vectorize), and the SoA loop lost to the AoS one. With it, this is the fastest number in the lesson.
  • clang vectorized the loop either way. Its check runs once per call, so removing it saves nothing that shows here.
  • **gcc -O2** does not work on several particles at once either way.

The promise is checked in Debug. Pass soa.positions as both arguments and the Debug build stops before the loop runs:

aos_vs_soa.rin:116: noalias parameters 'positions' and 'velocities' overlap

A Release build does not check. It runs on, and the lesson prints same result: no.

When AoS is right

When the code that touches a record touches most of its fields, AoS fetches nothing wasted, and keeping a record together is simpler. Data-oriented design does not mean SoA everywhere. It means choosing the layout from the loops that run over it. An entity component system is the case where many small loops each touch a few fields.

Try

  1. Run with --time in Release. Then remove tint, age, lifetime and name from particle and run again. The AoS loop should close most of the gap, because the struct shrinks toward what the loop reads.
  2. Go one step further than SoA: split positions into xs, ys and zs, arrays of f32, and the same for velocities. Write move_split and compare. Each loop is now a straight line over floats, which is the shape a compiler can vectorise.
  3. kayan stored positions as 16-byte vec4s. Change vec3 to four floats and see what it does to the bytes-per-step line and to the timing.
  4. Add a fade_soa system that only reads ages and writes tints. Its parameter list should say so, noalias included.
  5. Remove noalias from move_soa and build Release with gcc -O3. Compare --time, then compile with -fopt-info-vec and find "loop versioned for vectorization because of possible aliasing".
  6. Pass soa.positions as both arguments to move_soa. Run it in Debug, then in Release.

Lesson 2

One archetype table

src/2.archetype_table/archetype_table.rin

src/2.archetype_table/archetype_table.rin

Eight sparks in one table with three component columns, positions, velocities and lives, plus a numbers column that exists only so the output can say which spark is which. Each frame they move, they age, and the ones that ran out are removed.

Two rules

Columns never disagree. spark_spawn and spark_despawn are the only places rows come and go, and each touches every column. A new component means a new column, one line in each of those two procs, and one more argument to spark_spawn. A call site cannot add a row to some columns and forget the others.

Rows are packed. Systems loop over 0..count and never test whether a row is alive. Removing a row moves the last row into the hole:

spark 0 in row 0 expired; spark 7 moved from row 7 into it

That one copy per column is the whole cost of a despawn, whatever the table's size. The price is that a row number is not a name for a spark. After that line, "row 0" means spark 7. Lesson 4 adds names that do not move.

Removing while iterating

expire_system walks the rows backwards. When it removes row i, the row that moves in comes from the end, and the end has already been tested. A forward loop would have to stay on i after a removal, and it is easy to get wrong. Lesson 6 removes the question entirely by not removing anything during a loop.

Systems take slices

move_system(positions: noalias []vec2, velocities: []const vec2, dt) gets the rows in use, sparks.positions[0..sparks.count], and knows nothing about tables. []const says it only reads velocities. Each positions[i] is bounds checked in Debug, against the count rather than the capacity, so a system that runs past the live rows stops with a message instead of reading stale data.

noalias says that for the call, nothing else reaches the memory positions covers. Only the column the system writes needs it: a promise on the written column already rules out a write landing in the column being read. Without it, clang -O2 and gcc -O3 both vectorized this loop behind a run-time check that the two columns are apart. With it, neither checks. A Debug build checks the promise instead, once per call.

Status codes

spark_spawn returns spawn_status, an enum[must_use]: calling it and ignoring the result is a compile error. That is rin's convention for a proc that can fail: a status, with the result through an out-parameter. The ninth spark shows the full case.

Try

  1. Rewrite expire_system to walk forwards with a plain for. The output does not change, because no frame here expires a spark together with the one in the last row. Change two lives so that one does, and find the spark that outlives its life by a frame. Then fix the loop.
  2. Delete the line in spark_despawn that copies lives. What does the output show, and how long did it take to notice?
  3. Call spark_spawn without using its result and read the compiler's error. Then discard it on purpose with _ = spark_spawn(...).
  4. Make the table grow instead of reporting full: allocate double the capacity from the arena and copy every column across. Lesson 4's kayan_table_grow is one answer.

Four archetypes (rock, ship, bullet, turret) and four components (position, velocity, health, damage). One table type holds all four archetypes, and two queries decide which tables each system visits.

A table without a type

Lesson 2's table had one typed field per column. That cannot work for every archetype at once, so the columns become bytes:

table: struct = {
    signature: u64;
    count: u64;
    capacity: u64;
    columns: [component<>.count][*]u8;
}

columns[id] is null when the table has no such component. Its element size is component_info[id][0].size, where component_info holds each component's reflect record, position<>& and so on. table_add_row and lesson 4's moves work only from sizes, so they never need to know a component's type.

Types come back at the edges. column<T>(t) asks component_of<T>() for T's id, casts that column to [*]T, and returns it as a []T of the rows in use. component_of is one specialisation per component, one line each. Systems take []position, []velocity and so on, exactly as in lesson 2.

Sized by reflection

component has no count member at the end. component<>.count is the number of members, from the enum's reflect record, and it sizes both columns and component_info. With a hand-added count member the reflected count is one more than the number of components. That is how the bounds check found a bug while this lesson was being written.

components_check compares each enum member's name with the name in component_info. Swap two entries in component_info and the program stops before anything runs:

component 2 is health in the enum but damage in component_info

Different types, fewer checks

move_system takes noalias []position, as lesson 2's takes noalias []vec2, and for the same reason. One difference showed before either had noalias: clang vectorized this one without a run-time overlap check, and lesson 2's only with one. Here the two columns are different struct types, position and velocity, and clang reads C's type rules as saying they cannot share memory. In lesson 2 both are vec2. gcc checked in both. noalias makes the answer the same on both compilers, whatever the column types are.

Queries

moving: query = { .all = bit(component.position) | bit(component.velocity) };
healing: query = { .all = bit(component.health), .none = bit(component.damage) };

A table matches when it has every bit in all and none in none. moving visits ships and bullets. healing visits ships but not turrets, which have health but also deal damage. The output prints each visit.

Handles, slots, rows

kayan_entity: struct = { index: u32; generation: u32; }
kayan_slot:   struct = { generation: u32; table: u32; row: u32; }

A handle is what the rest of a program keeps. Its index picks a slot, and the slot says where the entity lives now. Rows move all the time: every despawn and every archetype change swap-removes. When one does, the table's entities column says which entity owned the moved row, and that entity's slot gets the new row number. Handles never change.

generation is what makes a handle safe to keep after its entity dies. Despawning bumps the slot's generation and frees the index, and the next spawn reuses the index with the new generation:

spawn d: it reuses a's index with the next generation
    d = 0:2 in table 0 row 2 {position velocity} at (4.0, 0.0)
    a = 0:1 is dead

kayan_alive is one comparison: the handle's generation against the slot's. A free slot already holds its next generation, which no handle carries yet, so no separate "alive" flag is needed. a cannot reach d's data, kayan_get returns null for it, and despawning it again returns kayan_status.dead and changes nothing.

Generations start at 1. A zeroed handle, {}, is 0:0, which never matches a slot, so it can stand for "no entity" without a separate flag.

Statuses

kayan_despawn, kayan_add, kayan_remove and kayan_move return kayan_status, an enum[must_use]: ok, or dead when the handle no longer names a live entity. Ignoring one is a compile error. The lesson discards them on purpose with _ = kayan_add<health>(...) where the handle is known to be alive.

Tables on demand

kayan_table_for(w, signature) looks the signature up in a hashmap<u64, u32> and makes the table if it is new. Nobody declares archetypes; they appear when an entity first needs that combination. Tables live in a vec<kayan_table> and are referred to by index, because adding one can move the whole list.

Tables start with room for 16 rows and double when full. The old columns stay in the arena unused, which is a waste these lessons accept. The last part of the program spawns 40 entities so the first table grows twice, despawns every other one, and checks the result two ways.

Checking the world

Reading back each survivor's position is a weak check. Swap-remove copies rows, so a stale row often still holds the right numbers. kayan_verify checks the invariant instead: every row of every table belongs to a live entity whose slot points back at that table and row, and the rows add up to the live count. It prints each problem it finds and returns how many there were. The lesson prints kayan_verify: 0 problems and fails if that is not so.

kayan_get also checks the slot's row against the rows in use, so in Debug a slot that points past the end of its table stops the program at the first lookup.

Moving between archetypes

give b health: b moves to a new table and keeps its position

kayan_add<health> computes signature | bit(health), finds or makes that table, appends a row, copies every component the two tables share, then swap-removes the old row. kayan_remove is the same move with the bit cleared. The inspector

src/5.inspector/inspector.rin

src/5.inspector/inspector.rin

A soldier and a crate, printed field by field by code that names no component type, then edited by component and field name, then a table layout report. Everything comes from the reflect records the world already holds for sizes.

What a reflect record has

T<> is a reflect record: name, size, align, kind, count, and for a struct, count fields. Each field has its name, offset, size, type ("f32" for a builtin, "array_16_c8" for a [16]c8), elem_type and array_count for arrays, and info, the record of the field's own type when it has one. A nested struct or an enum field has info; a builtin like f32 does not.

print_fields walks that. It takes the component's bytes as a []const u8, from kayan_get_bytes, and cuts each field's bytes out of it by offset and size, so a record that disagreed with the data would stop the program in Debug. Struct fields recurse through info, enum fields print their member name through reflect_name_from_value_or, a [16]c8 prints as text, and builtins print by type name. Because components are structs, even a single float like health.points has a name to print.

Tags

health: struct = { points: f32; max: f32; regen_timer: f32 @ "hidden"; }

@ "hidden" is a string attached to the field, read with reflect_field_has_attr. The inspector skips it. The component decides what a tool shows, and the tool does not need to know the component.

Names belong in tools

set_f32_by_name(w, e, "health", "points", 55.0) finds the component by name, the field by name, checks the field is an f32, and writes it. It refuses weapon.ammo, a u32, and the crate's health, which it does not have. That is the flexibility an editor or a console needs. It is also the string comparison kayan did in every query, once per archetype. Here it runs once per edit, and systems keep using ids.

Layout

print_layout lists each table's columns with size and alignment, and each column's bytes in use out of the bytes allocated for the table's capacity. It is the kind of report that shows when a component has grown padding, when a table has far more room than rows, or when a table carries a column most of its systems never read.

kayan

src/6.kayan/kayan.rin

src/6.kayan/kayan.rin

A turret at the centre, five wings of three drones, 140 frames. Seven systems run each frame, and every structural change they want goes through a command buffer applied at the end of the frame.

The frame

spawner    wings of drones enter                    records spawns
turret     shoot at the nearest drone               records spawns
movement   position += velocity * dt                writes
lifetime   bullets expire                           records despawns
collision  live bullets against drones              writes health, records despawn and add
burning    burning drones lose health               writes
outcome    destroy dead drones, catch leaks         records despawns
  blast    a destroyed drone hurts its neighbours   writes health, records adds
apply      every recorded change, in order

Writes to components happen in place, during queries. Changes to which table an entity is in are recorded, and applied once nothing is iterating.

Lifetime runs before collision, and collision skips bullets whose lifetime is used up. Those bullets are only still in their table because nothing structural happens until the end of the frame. Without the skip, a bullet that hit on its last frame would be despawned twice and counted as both a hit and a miss.

Systems and kernels

movement_system and burning_system are each a query and a kernel:

integrate: proc(ps: noalias []position, vs: []const velocity, dt: f32) -> void
burn: proc(hs: noalias []health, bs: []const burning, dt: f32) -> void

The system walks the tables and calls the kernel once for each table that matches. The kernel sees two columns, so the compiler sees a straight loop over two arrays. noalias qualifies parameters, so the loop needs a proc of its own to carry it; that is the only reason these two are split out. The output does not change.

Before the split, gcc -O3 vectorized both loops behind a run-time check that the columns were apart. After it, without the check. clang had no check either way, for the reason lesson 3 gives: the columns are different types.

lifetime_system stays one proc. Its loop records a despawn for each expired bullet, and a loop that calls something per row is not vectorized whatever its parameters say. The other systems branch, search or record in their loops too.

Why not change tables during a query

Each of these would be a real bug with the world from lesson 4:

  • Despawn. The swap-remove moves the last row into the hole, behind the loop, so that entity is not processed this frame. Meanwhile the slice the system cut before the despawn still reaches the old last row, a stale copy, and anything written to it is lost.
  • Spawn. A table that is full grows, and its columns move to new memory. A system holding a []position from before the spawn keeps writing to the old copy. Nothing crashes; the writes are just lost.
  • Add or remove. The entity moves to another table, which the same query may reach later. That entity is processed twice this frame.

The buffer

command: struct = { kind; entity; pending; signature; id; payload; }

Spawned entities have no handle until the buffer runs, so commands_spawn returns a pending number, and commands_set_spawned<T> writes a component into "the entity that pending spawn will create". T has to be in the spawn's signature, and applying the buffer stops the program with a message if it is not. Payloads are copies of the component value, kept as a []u8 in the buffer's frame arena next to the commands. commands_apply runs everything in order, then clears the arena. One memops_arena_clear frees the whole frame's commands.

Frame 113 is the interesting one. A bullet destroys one drone, and its blast takes two burning neighbours below zero in the same loop. Each of them is destroyed in turn, and each blast reaches back to drones already recorded as destroyed:

The blast cannot know 6:1 is doomed: its despawn is only recorded, and it is still in its table. So it records an add<burning> against it. When the buffer is applied the despawn comes first, and kayan_move reports kayan_status.dead for the add, so the command is skipped. The summary counts three.
